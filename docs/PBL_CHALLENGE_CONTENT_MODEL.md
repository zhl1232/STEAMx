# PBL 挑战内容模型

> 这份文档承接 [PBL_CHALLENGE_SYSTEM.md](/home/arron/work/docs/PBL_CHALLENGE_SYSTEM.md) 和 [PROJECT_CHALLENGE_MIGRATION_V3.md](/home/arron/work/docs/PROJECT_CHALLENGE_MIGRATION_V3.md)。
>
> 目标：定义“真正的 PBL 挑战”在内容层应该长什么样，避免挑战页退化成一句目标口号，或反过来退化成一份分步教程。

## 一、结论先行

真正的 PBL 挑战，不应该只给一个目标。

如果只有目标，用户通常不知道：

- 从哪里开始
- 什么算完成
- 卡住时该补什么能力
- 自己做出的方案和“照着教程做完”有什么区别

如果给完整标准步骤，挑战又会退化成普通项目教程。

因此，平台里的 `挑战` 更适合被定义为：

`一个真实任务 + 清晰约束 + 完成标准 + 可选脚手架 + 反思提交`

它本质上更像一份 `任务书`，而不是一份 `菜谱`。

---

## 二、挑战页回答的核心问题

一个合格的 PBL 挑战页，至少要回答下面 6 个问题：

1. 我到底要解决什么问题？
2. 为什么这是个值得做的真实任务？
3. 最后我要交出什么？
4. 在什么限制下完成？
5. 如果我不会做，可以从哪些小项目或技能开始补？
6. 做完之后，我需要怎样解释自己的方案和迭代过程？

如果其中任意 2-3 个问题没有回答清楚，挑战通常就会走向两个极端之一：

- 太空：只有目标，没有落地支撑
- 太满：步骤写死，没有探究空间

## 三、定义边界

### 1. 挑战不是项目教程

项目教程更适合承载：

- 单一技能
- 单次完成
- 明确步骤
- 可重复复现

例如：

- `纸张折叠桥`
- `杠杆投石机`
- `气球酵母发酵实验`

### 2. 挑战不是主题页

主题页更适合承载：

- 背景知识
- 案例合集
- 对象浏览
- 长期信息聚合

例如：

- 鸟类观察专题
- 桥梁结构专题
- 发酵现象专题

### 3. 挑战是综合任务

挑战更适合承载：

- 多因素取舍
- 多阶段推进
- 没有唯一标准答案
- 需要设计、测试、解释和迭代
- 最终要提交一个完整方案、作品或报告

一句话说：

`项目教你做一个小东西，挑战让你完成一个真实任务。`

## 四、PBL 挑战的最小内容结构

建议每个挑战至少包含以下 8 个部分。

这 8 个部分里，前 5 个是必须项，后 3 个是强烈建议项。

### 1. 情境 / 任务背景

作用：

- 把任务放进真实场景里
- 让用户理解“为什么要做”

推荐写法：

- 不直接说“做一个桥”
- 而是说“为 30cm 宽的沟设计一座轻量承重桥”

对应字段：

- `scenario`

### 2. 驱动问题

作用：

- 明确挑战不是拼手工，而是解决一个问题
- 给用户留下方案空间

推荐写法：

- 用一个问题把核心矛盾说清楚

例如：

- 怎样在材料有限的情况下同时保证跨度和承重？
- 怎样让弹射器在规则范围内更远且更稳定？

对应字段：

- `driving_question`

### 3. 目标产出

作用：

- 让用户知道最后要交什么
- 避免“做了一点东西但不知道算不算完成”

常见产出类型：

- 实物作品
- 演示视频
- 测试记录
- 设计说明
- 反思总结

对应字段：

- `expected_outcome`

### 4. 约束条件

作用：

- 逼出真实设计取舍
- 让不同用户的方案可比较

常见约束：

- 材料限制
- 尺寸限制
- 时间限制
- 预算限制
- 安全边界
- 提交形式限制

对应字段：

- `constraints`

### 5. 完成标准

作用：

- 让用户知道“完成”与“优秀”的区别
- 给审核、展示和互评提供统一框架

建议至少列 3-5 条。

示例：

- 能跨越指定距离
- 能承受最少 500g 重量
- 有至少 1 次明确迭代记录
- 能解释结构选择原因
- 提交过程照片或测试视频

说明：

当前数据结构里没有独立字段，短期可先写入 `expected_outcome` 或补充到 `constraints` / 页面模板中；后续建议加独立字段，如 `success_criteria`

### 6. 推荐脚手架

作用：

- 帮用户启动，但不规定唯一路径
- 让“不会做”的人知道先补什么

推荐拆成三类：

- `参考项目`
  作用：给灵感，不要求照做
- `前置技能`
  作用：补一个具体薄弱点
- `工具卡 / 资料卡`
  作用：在过程中随查随用

当前承载位置：

- `resources`（jsonb，type 收敛为 `project` / `skill` / `reference` 三分类，每条可带一句 `description`）
- 资料卡正文由独立的 `learning_resources` 表承载（`/resources/[id]` 详情页，可跨挑战复用）
- 详情页里的推荐项目区

#### 脚手架兜底规则

核心原则：**资料卡体系（`learning_resources`）是所有脚手架的兜底载体**——站内有现成实体就链实体，没有就写一张资料卡，保证任何挑战的脚手架都不会缺位。

- `参考项目`：优先链站内 `/project/[id]` 项目教程；没有合适的时，按下方「示例项目判断规则」决定是建配套示例项目，还是降级为一张 `case`（案例图解）型资料卡。
- `前置技能`：优先借用现有项目教程 / 训练营课时（写一句"补什么能力"的描述）；站内没有 → 写一张 `skill` 类资料卡（迷你讲解），后续平台内容丰富了可再把链接换成真实项目/课程。
- `资料卡`：独立可复用内容（原理讲解、材料对比、测试方法、技能迷你课等），一个挑战可挂多张，多个挑战复用同一张。

内容生产流程：创建挑战时先列出需要的 3-6 个脚手架清单 → 逐个匹配站内实体 → 缺口一律用资料卡补齐（或建配套示例项目），**不允许留空链接或省略关键脚手架**。

#### 示例项目判断规则

参考项目没有现成项目可链时，是否要建一个配套示例项目？三个条件，**至少满足前两条才建**：

1. **启动门槛高**：挑战核心产出是实物制作/多步操作，目标用户光看文字大概率不知道从哪下手——需要一个"看得见的完整样例"。若图文资料卡足以说明，则不建。
2. **有独立复用价值**：这个示例项目脱离挑战也能作为普通项目教程存在（出现在探索页、被非挑战用户完成）。只为单个挑战服务、独立价值低的不建。
3. **能做到"给灵感不给答案"**：示例必须演示*方法*而非*最优解*（如演示怎么做跌落测试，而不是展示最强保护结构），否则会导致提交趋同、违背 PBL 原则。做不到就降级为资料卡。

### 7. 分层提示

作用：

- 避免一上来把答案写完
- 在用户卡住时提供逐层支撑

推荐采用三层结构：

- `轻提示`
  只提醒方向，不给方案
- `中提示`
  给比较思路或注意点
- `强提示`
  给典型方法、常见坑或拆解路径

说明：

当前可先挂在 `stages[].hint` 或 `resources` 中，后续可考虑增加独立提示层级结构

### 8. 反思与迭代要求

作用：

- 让挑战真的体现 PBL，而不是一次性交作业
- 鼓励解释“为什么这样改”

至少应要求用户记录：

- 最初方案
- 遇到的问题
- 做过的修改
- 修改后的结果
- 最终反思

对应字段：

- `problem_statement`
- `iterations`
- `reflection`

## 五、推荐脚手架不等于标准路线

这是设计 PBL 挑战时最容易跑偏的一点。

### 1. 错误做法

把挑战页写成：

1. 先学 A
2. 再做 B
3. 然后跟着 C 拼出来
4. 最后提交

这会导致：

- 用户默认认为只有一条正确路径
- 提交内容高度同质化
- 挑战失去设计空间
- 反思变成形式化补字

### 2. 正确做法

把脚手架当成“遇到问题时可回查的支撑库”。

也就是：

- 挑战正文讲任务
- 小项目讲具体技能
- 用户自己决定何时回去补哪块能力

更合理的用户路径是：

1. 先理解挑战任务
2. 先尝试提出自己的方案
3. 发现卡点
4. 回查对应的小项目 / 技能卡 / 资料
5. 返回挑战继续做
6. 提交作品与迭代记录

一句话说：

`脚手架是支撑，不是路线图。`

## 六、挑战详情页推荐模块顺序

建议长期挑战详情页按下面顺序组织。

### 1. Hero 区

展示：

- 标题
- 一句话任务摘要
- 难度
- 类型
- 主 CTA

### 2. 任务说明

展示：

- 情境
- 驱动问题
- 目标产出

这部分应成为挑战页最先被读懂的主体。

### 3. 约束与完成标准

展示：

- 材料/时间/尺寸等约束
- 最低完成要求
- 优秀作品参考标准

### 4. 推荐脚手架

展示：

- 参考项目
- 前置技能
- 资料链接

注意：

- 视觉上应弱于“任务说明”
- 不要让用户误解为必须逐个完成

### 5. 阶段推进

展示：

- 推荐推进节奏
- 每一阶段的目标
- 可展开提示

注意：

- 阶段是“建议推进方式”，不是唯一解法

### 6. 提交要求

展示：

- 需要上传什么
- 需要写什么
- 是否公开
- 是否允许迭代更新

### 7. 作品墙 / 示例成果

展示：

- 已完成作品
- 精选案例
- 互评入口

### 8. 行动区

展示：

- 加入挑战
- 提交作品
- 查看脚手架

## 七、和当前数据结构的映射关系

| 内容层要素 | 当前字段 / 模块 | 是否够用 | 备注 |
| --- | --- | --- | --- |
| 情境 | `scenario` | 基本够用 | 可直接使用 |
| 驱动问题 | `driving_question` | 基本够用 | 可直接使用 |
| 目标产出 | `expected_outcome` | 基本够用 | 可直接使用 |
| 约束条件 | `constraints` | 基本够用 | 可直接使用 |
| 推荐脚手架 | `resources`（三分类 + description）+ `learning_resources` 资料卡表 + 推荐项目 | 够用 | type 已收敛为 `project` / `skill` / `reference`，资料卡有独立详情页 |
| 阶段推进 | `stages` | 基本够用 | 更适合写“建议推进”而不是硬步骤 |
| 分层提示 | `stages[].hint` | 不够清晰 | 后续可加提示层级 |
| 完成标准 | 无独立字段 | 不够用 | 建议后续加 `success_criteria` |
| 提交时反思 | `problem_statement` / `iterations` / `reflection` | 够用 | 已有实现基础 |

当前最明显的缺口是：

- 缺少单独的 `完成标准`（阶段层面已有 `stages[].checklist` 部分承载）
- 缺少真正分层的 `提示系统`

## 八、内容生产规则

为了让挑战保持 PBL 形态，建议内容侧执行以下规则。

### 1. 标题规则

标题应体现任务，而不是学科主题。

更好：

- `轻量承重桥挑战`
- `未来社区规划挑战`
- `密室谜题设计挑战`

较差：

- `桥梁设计`
- `城市规划`
- `谜题入门`

### 2. 摘要规则

摘要要同时包含：

- 场景
- 行动
- 目标

避免只有口号式描述。

### 3. 脚手架规则

每个挑战最多给 3-6 个强相关脚手架。

不要一次塞进太多“相关内容”，否则会让用户误以为要先学完一堆东西才能开始。

### 4. 提示规则

提示要默认折叠。

只有在用户主动展开时，才逐层暴露更具体的支撑。

### 5. 反思规则

反思区不要只问“你学到了什么”。

更有效的问题是：

- 你最初的方案是什么？
- 它在哪一步失败了？
- 你改了什么？
- 为什么这次改动更有效？
- 如果再做一次，你会先改哪里？

## 九、一个完整示例

以 `轻量承重桥挑战` 为例。

### 任务背景

学校要跨过一条 30cm 宽的小沟，需要一座尽量轻但能承重的桥。

### 驱动问题

怎样在材料有限的情况下，同时提高桥的跨度、稳定性和承重能力？

### 目标产出

- 一座桥梁模型
- 一段承重测试视频
- 一份结构说明
- 一次以上迭代记录

### 约束条件

- 只能使用纸张、冰棍棒、胶带、白胶
- 总材料数量受限
- 桥面必须跨越 30cm
- 测试时桥面不能明显塌陷

### 完成标准

- 能稳定跨越 30cm
- 能承受至少 500g
- 有清晰测试记录
- 能解释结构选择
- 至少有 1 次修改迭代

### 推荐脚手架

- 参考项目：`纸张折叠桥`
- 前置技能：`桁架结构受力入门`
- 资料卡：`常见桥型对比`

### 分层提示

- 轻提示：想一想，桥面变形最严重的位置在哪里
- 中提示：对比平板结构和三角结构在受力时的差异
- 强提示：如果桥面中段下垂，优先考虑提高截面高度或加入桁架

### 反思要求

- 你的第一版为什么失败或不稳定
- 你改动了哪些结构
- 承重结果如何变化

这个例子里，挑战页给了足够清晰的任务框架，但没有把方案写死。

## 十、产品判断标准

如果未来要判断一个挑战页面写得像不像真正的 PBL 挑战，可以用下面 5 条快速检查：

1. 用户读完后，是否知道自己要解决什么真实问题？
2. 用户是否知道最后要提交什么，而不是只知道“做一做看”？
3. 页面是否给了脚手架，但没有把路径写死？
4. 页面是否要求解释方案、记录试错，而不仅是上传成品？
5. 不同用户是否有可能提交明显不同但都合理的方案？

如果第 3 条和第 5 条不成立，这个挑战通常还是“教程伪装成挑战”。

如果第 2 条和第 4 条不成立，这个挑战通常只是“活动标题”，还不是完整的 PBL 任务。
