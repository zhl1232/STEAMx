# 项目内容审计 V1

> 审计对象：`public/projects/generated/manifest.json` 中的 399 个项目标题
>
> 审计目标：按新的内容边界，判断哪些项目应该保留，哪些需要改名细化，哪些应该上移为挑战，哪些应移出项目层进入观察域。

## 一、这轮审计采用的新边界

### 1. 项目（Project）

项目不再承担完整 PBL，也不承担完整观察逻辑。

项目层只保留这类内容：

- 一个明确的小技能
- 一个清晰的局部动作
- 一个可在一次短周期内完成的小产出
- 可以被挑战聚合，但本身不是完整挑战

判断标准：

- 用户看到标题后，应该能立刻知道“我要做哪一个动作”
- 项目应尽量避免“长期记录”“综合调查”“完整设计命题”“开放式优化竞赛”

### 2. 挑战（Challenge）

挑战承担真正的 PBL 目标。

挑战层适合承载：

- 明确目标
- 多阶段推进
- 综合能力整合
- 开放式优化
- 比赛机制或长期任务

典型信号：

- 标题里带 `挑战`
- 需要组合多个技能项目才能完成
- 结果不是单一小作品，而是一个较完整的解决方案

### 3. 观察域（Observation）

观察逻辑不再放在项目层。

应移出项目层的内容通常具备这些特征：

- 以连续观察为核心
- 以物种 / 地点 / 时间 / 记录为核心
- 以图鉴、调查、追踪、观察日记为主要形式
- 价值在于长期沉淀和结构化记录，而不是一次性完成某个小技能

## 二、总体结论

399 个项目做第一轮审计后，建议如下：

| 结论 | 数量 | 说明 |
|---|---:|---|
| 暂时保留 | 330 | 标题已足够具体，基本符合“小技能学习”定位 |
| 改名并细化 | 31 | 方向可以保留，但标题仍偏泛，需要收窄为明确动作 |
| 上移为挑战 | 15 | 更适合作为 PBL 挑战，不应继续留在项目层 |
| 移出项目层，归入观察域 | 23 | 核心价值是观察、记录、调查，不应作为项目存在 |

当前最大问题不在整库平均分布，而在以下三个集中区域：

- `科学 / 动物观察、植物观察、地球与天空` 中混入了大量完整观察逻辑
- `工程 / 桥梁建造、简易机器` 中混入了多个本质上是挑战的题目
- `数学 / 数学游戏、逻辑谜题` 中混入了若干研究型、分析型、主题型标题

## 三、建议保留的总方向

这批子类整体健康，暂不建议大动：

- 科学 / 物理实验
- 科学 / 化学实验
- 技术 / 电子制作
- 技术 / 机器人（除个别条目）
- 工程 / 机械结构（除个别条目）
- 艺术 / 手工
- 艺术 / 雕塑

这类内容多数已经符合“小技能学习”定位：

- `自制指南针`
- `水果电池`
- `电磁铁起重机`
- `纸板齿轮联动`
- `木工收纳盒`
- `石膏面具制作`

## 八、对子分类的结构性判断

### 1. 动物观察 / 植物观察 / 地球与天空

这三个子类目前最大的问题，不是个别标题写得不够好，而是整体混入了太多“观察体系”。

后续建议：

- 把长期观察、图鉴、调查、追踪统一迁到观察域
- 项目层只保留“识别方法”“记录方法”“简单实验”“一次性制作”这类技能卡
- 对应的长期任务放到挑战或观察记录系统里

### 2. 工程

工程类的核心问题是：

- 小项目和综合命题混在一起
- “优化”“挑战”“综合设计”没有上移

后续建议：

- 项目只保留具体结构或机构技能
- `优化、竞赛、综合设计` 一律优先做挑战

### 3. 数学

数学类的核心问题是：

- 一部分内容是清晰练习题
- 一部分内容是研究主题或分析报告

后续建议：

- 项目层保留可操作的单个谜题、单个模型、单个规则体验
- “研究 / 分析 / 建模 / 策略”类标题要么收窄，要么上移

## 九、接下来的落地顺序

建议按下面顺序推进，不要一次性全部重写：

1. 先冻结新的内容边界：项目 = 小技能，挑战 = PBL，观察 = 独立域
2. 先处理 `移出项目层` 和 `上移为挑战` 的条目，避免继续误生成内容
3. 再批量处理 `改名并细化` 的项目
4. 最后再进入每个项目的正文重写

## 十、这份 V1 的定位

这份文档是第一轮结构审计，不是最终命名稿。

它解决的是：

- 哪些项目不该继续留在当前层级
- 哪些项目需要收窄
- 哪些项目其实应该变成挑战

它还没有做的事情：

- 399 个项目的最终改名定稿
- 每个项目的正文模板重写
- 观察域和挑战域的具体内容重组
