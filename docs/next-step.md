## 下一阶段主线：PBL 项目工作台 + AI Agent 导师

### 方向判断

- **优先级**：P0。
- **产品定位**：先把 PBL 项目流程做成核心体验，再把 AI Agent 嵌进流程里做“项目导师”，而不是先做一个泛化聊天机器人。
- **原因**：项目已有挑战、训练营、作品提交、XP/徽章、个人主页和自然观察等模块；PBL 工作台可以把这些能力串成一条可完成、可反馈、可展示的学习闭环。
- **后置事项**：个性化 STEAM 成长路径可以基于 PBL 数据继续做，但不作为当前最优先方向。

### MVP 范围

- **入口**：优先放在 `/create` 和现有 `/pbl/[id]` 挑战详情里；用户选择挑战后进入项目工作台。
- **工作台核心结构**：
  - 项目目标：用户用一句话描述要解决的问题或作品方向。
  - 阶段任务：围绕 PBL 拆成 3-5 个阶段，例如理解问题、设计方案、动手制作、测试改进、成果发布。
  - 过程材料：每个阶段可记录文字、图片、作品链接或 Scratch 作品。
  - 检查点反馈：每阶段提交后获得导师反馈和下一步建议。
  - 最终总结：生成作品说明、反思记录、STEAM 能力标签，并衔接挑战投稿或个人主页时间线。

### AI Agent 职责边界

- **拆题**：根据挑战目标、用户年级/能力、可用材料，生成项目计划、阶段任务和检查点。
- **提示**：用户卡住时给可执行提示，优先引导思考，不直接代做完整答案。
- **评审**：基于阶段材料给反馈，指出已完成内容、不清楚的证据和下一步改进。
- **总结**：项目结束时帮助整理公开作品说明、学习反思和 STEAM 能力收获。

### 非目标

- 暂不做复杂多 Agent 编排。
- 暂不做长期跨项目记忆。
- 暂不让 Agent 自动替用户发布、报名或提交审核。
- 暂不做开放式工具调用；所有 AI 行为都应绑定在 PBL 阶段任务内。

### 建议迭代顺序

1. **P0：PBL 工作台骨架**
   - 新增“开始项目/继续项目”流程。
   - 支持目标、阶段任务、阶段状态、过程材料、最终总结。
   - 先用静态模板或规则生成阶段任务，不依赖 AI。

2. **P0：导师 Agent API**
   - 提供受限接口：拆题、提示、评审、总结。
   - 输入必须包含挑战信息、当前阶段、用户已有材料。
   - 输出结构化 JSON，前端只渲染受控字段。

3. **P1：挑战与作品闭环**
   - 工作台完成后可一键整理为挑战投稿草稿。
   - 审核通过后同步 XP、徽章、金币、个人主页时间线。
   - 在 `/pbl/[id]` 显示“我的项目进度”和继续入口。

4. **P1：过程反馈体验**
   - 每阶段显示导师反馈、改进清单和证据缺口。
   - 增加“我卡住了”“帮我检查”“生成总结”等明确动作按钮。

5. **P2：个性化成长路径**
   - 基于 PBL 完成记录、STEAM 雷达图、课程进度、自然观察进度，推荐下一条学习路径。
   - 可进入个人主页作为“下一步行动”的增强版。

### 初版验收标准

- 用户能从一个 PBL 挑战进入工作台，并保存自己的项目进度。
- 用户能完成至少 3 个阶段，每阶段有任务、材料和状态。
- Agent 能完成 4 个受限动作：拆题、提示、评审、总结。
- 最终总结能转成挑战投稿草稿或作品说明。
- 未登录、无权限、审核中/已结束挑战等状态有清晰限制。

## AI Tutor Agent 化深度集成

### 方向判断

- **优先级**：P1（在 PBL 工作台 + 受限导师 Agent MVP 落地后推进）。
- **产品定位**：在现有 `lib/ai/tutor` 与多模态视觉（Qwen Vision）基础上，将小迪从「对话式导师」升级为可调用工具的 Agent，能直接与产品 UI 交互，而不只是输出文字建议。
- **技术基础**：已有 tutor 引擎、场景上下文（`surface` / `lessonId` / 物种 slug）、图片三类来源、代币门禁与对话线程；可复用 Qwen Vision 做棋盘/积木块识别。

### 架构要点

- **MCP 服务扩展**：引入 MCP 服务扩展 AI 技能池；新增技能服务命名遵循 `xxx-skill` 后缀规范（与现有 Cursor skills 命名习惯对齐），便于注册、发现与权限隔离。
- **工具调用边界**：Agent 行为仍绑定在用户当前场景内（Scratch 课时、扫雷/迷宫 Playground、PBL 阶段等），不做开放式任意系统操作。
- **典型能力示例**：
  - **Scratch 卡关**：根据用户描述或截图，自动高亮提示应对应的 Scratch 积木块（DOM/编辑器 API 联动）。
  - **扫雷 / 迷宫**：基于当前棋盘状态的动态 BFS 寻路提示，在棋盘上可视化下一步可走格，而非只给文字解法。
  - **PBL 阶段**：在「我卡住了」流程中，除文字提示外可高亮工作台内缺失的检查项或相关材料入口。

### 非目标

- 暂不做跨页面无约束的 UI 自动化（如代用户点击提交、代发帖）。
- 暂不做多 Agent 编排或长期自主任务链。
- MCP 工具集先覆盖 Playground 与 Scratch 等高价值卡点场景，再逐步扩展。

### 建议迭代顺序

1. **P1：Agent 运行时骨架** — tutor 流式回复之外增加结构化 tool call 通道；前端注册场景级 tool handler。
2. **P1：首个 MCP skill** — 例如 Scratch 积木高亮或迷宫 BFS 提示，端到端验收一条「对话 → 调工具 → UI 反馈」链路。
3. **P2：技能池运营** — 按 `xxx-skill` 规范沉淀更多场景 skill，Admin 可配置启用范围与代币消耗策略。

## 自然观察：地域化与动态预警

### 方向判断

- **优先级**：P2（自然观察核心流与物种库稳定后推进）。
- **产品定位**：在现有丰富生态（物种百科、观察记录、地图、社群鉴定、季节/生境档案）上，结合**地理围栏**与**时令数据**，做地域化运营与动态季节活动，增强户外探索的沉浸感与回访动机。
- **与现有能力关系**：复用 `nature-topics`、物种 slug、观察提交与 XP/徽章；与个人主页「自然待观察物种」、小迪 species 场景可联动推送。

### 能力范围

- **地域物种库**：针对特定地域（如北京）维护本地物种子集或运营位（常见候鸟、公园特色昆虫/植物），与全国物种库并存，首页/专题页可切换或按用户定位推荐。
- **时令与活跃期**：接入迁徙季、羽化期、开花期等信号；当特定物种进入活跃窗口（如黄眉柳莺迁徙季、某昆虫羽化高峰）时触发运营事件。
- **季节限时打卡挑战**：动态生成「本季必观察」清单或限时挑战（打卡 N 种本地当季物种），完成发放专属徽章/时间线条目；推送入口可进个人主页「今日行动」与自然频道 Banner。
- **地理围栏（可选）**：用户授权定位后，在公园/保护区范围内增强物种提示或「此地常见」卡片；未授权时仅按手动选择的城市/地区展示。

### 非目标

- 暂不做实时物种追踪或第三方生态 API 强依赖（先运营配置 + 规则引擎）。
- 暂不做全站强制 LBS；地域化内容为增强层，默认行为与现网一致。

### 建议迭代顺序

1. **P2：地域与季节配置模型** — 后台可配置「地区 × 物种 × 时间窗口」运营单元。
2. **P2：动态挑战生成** — 按当前日期与地区渲染限时打卡任务，接入现有提交与徽章体系。
3. **P3：定位与围栏** — 可选 GPS 围栏、本地化推送与地图层「当季热点」展示。

## 游乐场：实时对战与协作 (Real-time Multiplayer)

### 方向判断

- **优先级**：P1（单机 Playground 体验稳定、留存数据验证后再上多人）。
- **产品定位**：`app/playground` 已集成五子棋、数独、扫雷、迷宫、排序竞速等 15 款硬核游戏，当前以单机逻辑为主（结合 `lib/playground/storage` 本地/云端成绩）。利用底层 Supabase **Realtime（WebSockets）** 升级为可匹配、可邀请、可协作的多人体验，提升青少年留存与社区活跃度。
- **技术基础**：Supabase 已接入；游戏逻辑集中在 `hooks/playground/`；小迪 playground 场景可后续与双人协作提示联动（参见 AI Tutor Agent 化）。

### 能力范围

- **匹配对战**：五子棋（gomoku）、排序竞速（sorting-race）等竞技向游戏支持快速匹配或排位对战；落子/完成时间经 Realtime channel 同步，服务端或 RLS 校验回合合法性。
- **开房邀请**：生成房间码或分享链接，好友加入同一对局；支持观战（可选 P2）。
- **双人协作**：迷宫、扫雷等解谜类增加协作模式——双方共享棋盘状态、分工揭格或分头探路，胜利条件与单机区分（如共同到达终点、合并揭雷进度）。
- **房间生命周期**：创建 → 等待 → 进行中 → 结束；断线重连、超时判负、平局规则需按游戏类型分别定义。

### 非目标

- 暂不做全 15 款游戏一次性多人化；优先 1–2 款验证 Realtime 架构（建议五子棋 + 一款协作向）。
- 暂不做跨房间语音/聊天（可复用现有消息体系另行规划）。
- 暂不做真钱或站外赌注；对战奖励走现有 XP/金币体系且需防刷。

### 建议迭代顺序

1. **P1：Realtime 房间模型** — 数据库表（房间、参与者、对局状态）、Supabase channel 约定、通用 `useGameRoom` hook。
2. **P1：五子棋对战 MVP** — 匹配队列或开房二选一，完整一局可玩并写入成绩/统计。
3. **P2：排序竞速对战** — 同题竞速、实时排行榜条。
4. **P2：迷宫/扫雷协作** — 共享状态同步与协作胜利结算。
5. **P3：游乐场大厅** — 在线人数、热门房间、邀请入口与社区动态联动。

## 动态经济系统与赛季/限时运营 (Dynamic Economy & Seasons)

### 方向判断

- **优先级**：P1–P2（XP/金币/徽章/商店闭环已具备，适合在核心学习路径成型后叠加运营层）。
- **产品定位**：当前 `lib/shop/items.ts` 商品与 `lib/badges.ts` 徽章以静态配置为主。引入**通行证（Battle Pass）**、**探索季/观鸟季**等限时运营单元，让奖励与任务随赛季动态变化，支撑教育社区产品的长期生命力与回访节奏。
- **与现有能力关系**：复用 XP、coins、badges、shop、挑战投稿、自然观察、PBL 进度；Admin 后台可扩展赛季配置；与个人主页「本周探索计划」「今日行动」可展示当季任务进度。

### 能力范围

- **赛季（Season）配置**：后台定义赛季名称、起止时间、主题视觉（如「春季迁徙观鸟季」）、免费轨/付费轨奖励表（若暂不收费可仅做免费轨 + 进阶任务解锁）。
- **赛季任务与进度**：赛季内任务池——完成指定 PBL 挑战、提交 N 条自然观察、游乐场对战胜场等；进度条升级解锁等级奖励。
- **动态倍率与限时商品**：赛季期间特定行为金币倍数（如观鸟观察 2× coins）；商店轮换限时头像框、名字颜色等绝版虚拟物品（赛季结束下架或绝版标识）。
- **绝版与收藏**：赛季专属徽章/头像框计入徽章墙与资料页展示；与现有阶梯徽章体系并存，系列用 `seasonId` 区分。
- **跨模块联动**：与自然观察「地域化与动态预警」、PBL 工作台可共用同一赛季 ID，避免多套运营配置打架。

### 非目标

- 暂不做复杂二级市场或玩家间交易。
- 暂不强制 IAP；首版以免费通行证 + 任务驱动为主，付费轨预留数据模型即可。
- 暂不做跨赛季积分继承（每季清零或仅保留收藏展示）。

### 建议迭代顺序

1. **P1：赛季数据模型** — `seasons`、`season_tiers`、`season_tasks`、用户赛季进度表；Admin CRUD 与上下线时间。
2. **P1：首季 MVP（观鸟/探索主题）** — 前端赛季页入口、任务列表、等级奖励领取；接入现有 coins/徽章发放流水。
3. **P2：动态商店轮换** — 商店按赛季过滤/高亮限时商品；倍数规则引擎（行为类型 × 赛季配置）。
4. **P2：全站赛季触点** — 首页 Banner、个人主页进度卡、挑战/自然频道赛季标签。
5. **P3：通行证进阶** — 更长周期、更多任务类型、与游乐场多人战绩挂钩。

## 自然观察:观察种类扩展规划

### 方向判断

- **优先级**:P2(在现有鸟/虫/植物专题与物种库稳定后推进)。
- **背景**:参考《北京自然观察手册》系列(鸟类、海鲜河鲜、树木、野花、云和天气、昆虫、蔬菜、园林花卉、矿物和岩石、水果干果),评估如何归入现有自然观察。
- **核心认知**:观察系统本质是「有限类型清单 + AI 鉴定 + 社群共识 + 已观察/待观察进度」引擎,并非生物专用。只要某类对象能列成有限、可枚举的类型清单即可复用;生命阶段/性别本就是可选字段,非生物专题隐藏即可。

### 分类结论

- **植物专题(`plants`)**:语义从「树木」放宽为「植物」,吸收 **树木 / 野花 / 园林花卉 / 蔬菜 / 水果干果**。不为它们单开专题,改用物种属性标签区分:
  - `life_form`:乔木 / 灌木 / 草本
  - `cultivation`:野生 / 栽培
  - `use`(可选):食用(用于标记蔬菜、水果干果)
- **矿物岩石**:新增非生物专题。类型清单稳定、可鉴定、可共识,改造量小;隐藏生命阶段/性别,保护提示改为「不破坏地貌、不私自采集」类文案。
- **云**:可做,但只做「云的类型」(按国际云图约 10 个云属建有限清单,可鉴定/共识/进度);**天气状态(晴/雨/雪)不做专题**,如需保留只当观察记录里的环境标签。
- **真菌**:暂缓。当前无物种数据,清单是系统地基,有数据再启用。
- **海鲜河鲜**:暂缓或不做。三类食材中与「自然观察」距离最远(纯菜场/餐桌动物),且无水生动物专题,需新建水产清单 + 改文案,投入大、收益虚。

### 非目标

- 不为野花/园林花卉/蔬菜/水果各开独立顶层专题(统一并入植物 + 标签)。
- 非生物专题不套用生命阶段/性别/保护放归等生物专属字段与文案。
- 不做「天气状态」类无法枚举成清单的对象。

### 建议迭代顺序

1. **P2:植物专题扩容** — 加 `life_form` / `cultivation` / `use` 属性与对应物种导入;放宽专题文案与专题图。
2. **P2:矿物岩石专题** — 新增 `nature_topic`,配岩矿类型清单,隐藏生物专属字段,改写提示文案。
3. **P3:云类型专题** — 按云属建类型清单,复用鉴定/共识/进度;不含天气状态。
