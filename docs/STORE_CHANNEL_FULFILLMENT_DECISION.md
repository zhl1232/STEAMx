# 实物商城渠道与履约方案（淘宝外部结算优先）

> 决策日期：2026-08-23
>
> 适用项目：STEAMX · 史迪姆实物材料包商城
>
> 本版是在 2026-08-22 方案上的修订：把“淘宝商品卡片 + 淘宝完成支付”确定为当前落地路线。
>
> P0 状态（2026-09-09）：代码与迁移已落地；上线前仍需由运营配置真实淘宝链接并完成小额真实订单验证。数据库商品是否已配置、链接是否有效不由本文件臆测。

## 结论

当前不申请 1688 的“铺货分销”ISV/插件方案，也不把 STEAMX 建设成服务其他商家的分销工具。站点暂时没有公司主体，也达不到部分平台/ERP 的订单门槛，因此不把 1688 自动下单、聚水潭或其他需要企业资质的 ERP 作为启动条件。

第一阶段采用 **STEAMX 展示商品，淘宝店完成交易**：

```text
用户在 STEAMX 浏览商品卡片
    -> 点击「去淘宝购买」
    -> 在淘宝 App/网页完成登录、支付和地址确认
    -> 淘宝商家负责发货、物流、退款和售后
```

STEAMX 仍然维护商品标题、图片、说明、参考价格和淘宝链接，但不在本站伪造“已支付”或“已下单”状态。商品卡片会明确提示：实际支付、物流和售后以淘宝订单为准。

## 第一阶段：淘宝外部结算（现在执行）

### 业务边界

- 新上架商品应优先选择 `external` 外部结算模式，渠道为 `taobao`；数据库仍以 `internal` 作为兼容默认值，避免未配置链接的历史商品突然失效。
- 商品卡片是 STEAMX 自己的展示层，按钮使用受限的 `https` 淘宝/天猫链接，打开淘宝 App 或网页；不使用 iframe，不抓取用户淘宝 Cookie，也不代收淘宝支付信息。
- 淘宝订单号、付款状态、物流和售后以淘宝侧为准；STEAMX 只保存商品目录和渠道链接，不把外部订单冒充为本站订单。
- 价格、库存和规格在早期采用人工核对/更新。卡片文案应避免承诺实时库存、运费或发货时效。
- `/store/orders` 与本站订单模型保留作过渡和未来自有支付使用；外部淘宝商品不进入本站购物车、地址采集和待支付订单流程。
- 商品不只放在商城目录：可用 `course:ID`、`lesson:ID`、`project:ID` 关联到课程、课时零件清单和项目材料区，在用户产生材料需求的上下文中展示同一张淘宝卡片。

### 淘宝客链接的使用边界

淘宝客/联盟链接在技术上可以作为推广链接，但不是当前履约方案的前提：

- 自有淘宝店优先使用普通商品或店铺链接，不能把“自购返佣”当作收入模型。
- 只有在商品、推广位和账号符合淘宝联盟规则时，才考虑把联盟 `click_url` 作为可选渠道链接。
- 联盟规则、联合营销协议和类目限制可能变化；未确认资格前不承诺佣金、不在前台宣传“返佣”。

### 当前操作清单

1. 开通并维护淘宝店，确认店铺主体、类目、收款和发货能力符合淘宝要求。
2. 在 STEAMX 商品记录中配置淘宝渠道、商品链接和展示信息。
3. 上架前人工核对商品页、规格、价格、库存、运费和售后说明。
4. 每周（或有流量时更频繁）复核链接与库存；发现失效或涨价先暂停卡片。
5. 用小额真实订单验证“点击 → 淘宝下单 → 商家发货 → 售后”闭环，再扩大商品数量。

## 商品应该出现在哪里

商城目录是“找商品”的入口，但课程、课时零件清单和项目材料区是“已经知道要买什么”的入口。当前采用两层展示：

1. **上下文优先**：在材料需求旁显示 1～3 个匹配材料包，直接告诉用户它适配哪门课/哪个项目。
2. **商城兜底**：在 `/store` 保留完整目录，方便用户比较和再次购买。

上下文卡片不遮挡课程学习、不自动弹窗、不把购买作为完成课程的条件；它只在确实配置了匹配商品和有效淘宝链接时出现。这样既减少用户从课程页跳出去找材料的步骤，也避免全站到处重复推销。

## 第二阶段：低成本人工履约兜底（按需）

如果某些商品暂时没有合适的淘宝链接，或需要测试供应商，可以继续保留少量固定 SKU 的人工采购流程：

```text
用户通过已确认的站内支付（未来启用）
    -> 后台生成采购任务
    -> 管理员手动在 1688/供应商处下单
    -> 供应商按地址代发
    -> 管理员回填物流和售后结果
```

当前不把这条流程宣传为已开通的在线支付能力，也不启用未经确认的 1688 自动下单接口。它只是运营备选，不应阻塞淘宝商品卡片上线。

## 第三阶段：达到条件后再做开放平台/自建履约

当出现稳定订单量、可承担售后和对账成本，并具备公司主体及相应平台资质后，再评估：

1. 淘宝/天猫开放平台：按官方权限接入商品、库存、订单、物流和售后读写，先做只读同步，再逐步开放写操作。
2. 合规 ERP（如平台服务市场中的成熟产品）：先核对授权范围、隐私处理、自动付款、服务费、退款和数据导出，再决定是否使用。
3. 自建履约服务：统一商品、SKU、库存、订单和物流事件；保留人工回退和审计日志。

进入第三阶段的门槛：

- 已有合法主体、收款和平台开发者资格；
- 连续数周的真实订单量足以覆盖接口、客服和售后成本；
- 能明确承担个人信息、支付、税务和退款责任；
- 先完成沙箱/小流量灰度、幂等、重试、告警和人工回退测试。

## 技术落地状态与后续计划

### P0（已落地，待运营验收）

- 迁移 `20260823100000_store_external_checkout.sql` 增加 `checkout_mode`、`external_channel`、`external_url`，旧商品默认仍为站内模式；`20260823110000_store_context_keys.sql` 增加课程/课时/项目上下文关联。
- `lib/store/external-channel.ts` 和商品管理 API 限制外部渠道为淘宝，并只接受淘宝/天猫 HTTPS 链接；公开商品 API 通过 `mapPublicStoreProduct` 清除供应商、1688 offer/spec 和 metadata。
- `/store` 按渠道渲染商品卡片：淘宝商品显示“去淘宝购买”和外部支付提示，不进入本站购物车；无有效链接时显示待配置且不可购买。
- 课程详情、课时零件清单和项目详情通过上下文键展示匹配淘宝材料包；`/admin/store` 提供管理员配置入口。
- 站内报价/订单流程拒绝以 API 绕过外部商品卡片；相关本站订单能力继续作为兼容和后续自有支付路径。

P0 完成只表示代码路径已具备，不表示真实淘宝商品、库存或履约已经验收。运营仍需完成店铺准备、商品配置、人工核对和小额真实订单闭环。

### 免费变现历史方案（存档，不是当前商城履约前提）

早期讨论过淘宝客/联盟、自购返佣、免费内容导流等变现方式。这些方案不改变当前履约边界：自有淘宝店普通链接优先，未确认联盟资格、推广位和类目规则前不承诺佣金，也不把“自购返佣”写成收入模型。免费课程、金币商店或其他免费体验属于产品/商业策略，不能被解释为已启用的淘宝联盟变现，也不应驱动商品 API、订单状态或 1688 自动下单。

### P1（淘宝店稳定后）

- 增加链接健康检查、失效/价格变更提醒和人工下架开关；不做浏览器自动化下单。
- 记录点击量、外部渠道标识和人工同步时间，但不记录淘宝登录态或支付敏感信息。
- 根据实际售后咨询决定是否增加“淘宝订单号自愿登记”的客服辅助字段；不把它当作自动对账。

### P2（达到第三阶段门槛后）

- 先接入官方只读商品/订单同步，再做库存和物流回写；每一步都保留人工回退。
- 评估 ERP 与开放平台的总成本，只有收益明确时才替换人工流程。
- 单独提交平台资质、隐私、支付和数据留存评审，不把 P2 代码提前打开。

## 验收标准

- 用户能在 STEAMX 看懂“在哪里付款”，点击后在淘宝完成交易；页面不出现 iframe 收银台或虚假的站内支付成功。
- 外部商品不会进入本站地址采集、购物车、待支付订单或 1688 自动下单队列。
- 非淘宝、非 HTTPS 或格式异常的链接不会被公开返回；管理员保存时有明确错误提示。
- 没有淘宝链接的商品显示“链接待配置”并不可购买，而不是回退到未配置支付的本站订单。
- 旧的 1688 OAuth/同步代码仍可保留作后续研究，但后台默认不引导连接、不启用 `alibaba.trade.fastCreateOrder`。

## 明确不做

- 不申请 1688“铺货分销”插件来服务其他商家；
- 不以 1 万/月等高门槛 ERP 作为当前上线前提；
- 不要求没有公司主体时注册聚水潭或同类企业 ERP；
- 不把淘宝、抖店、微信小店的完整收银台直接 iframe 嵌入；
- 不使用 `1688-cli` 浏览器自动化作为正式无人值守履约方案；
- 不在未确认接口权限和订单协议前启用旧的 `alibaba.trade.fastCreateOrder`；
- 不把淘宝客自购返佣当作 STEAMX 的核心商业模式。
