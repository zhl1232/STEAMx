# 实物商城渠道与履约方案结论

> 决策日期：2026-08-22
>
> 适用项目：STEAMx 实物材料包商城

## 结论

STEAMx 当前不申请 1688 的“铺货分销”ISV/插件解决方案，也不把自己建设成面向其他商家的分销工具。

原因是该类方案面向为下游电商或内容平台商家提供铺货、订单回流和代发能力的 ISV。它要求平台方案、应用权限、订单回流和运营门槛，和 STEAMx 自己售卖材料包的业务不是同一个场景。自动铺货只有在商品需要进入抖店、微信小店、拼多多等外部店铺时才有意义。

## 当前阶段：STEAMx 自有商城 + 人工采购

当前先保留 STEAMx 自有商城，商品只上架少量固定材料包或固定 SKU。

流程：

```text
用户在 STEAMx 下单并支付
    -> 后台生成待采购任务
    -> 管理员在 1688 手动采购固定货源
    -> 1688 商家按用户地址一件代发
    -> 管理员把 1688 订单号和物流单号填回 STEAMx
    -> STEAMx 更新订单发货状态
```

这一阶段不依赖 1688 AppKey/AppSecret、1688 OAuth 或自建 ISV 方案。订单、加密收货地址、固定货源映射和履约事件仍保留在项目内，但不启用未经确认的 1688 自动下单接口。

## 后续阶段：平台店铺 + 合规 ERP

当订单量值得自动化时，再开通一个外部销售渠道：

1. 微信小店/视频号小店：适合微信私域和家长用户。
2. 抖店：适合需要抖音流量和平台内成交的场景。

在对应平台的服务市场订购已经存在的 ERP/分销代发工具，由 ERP 负责：

- 平台订单同步；
- 商品与 1688 货源、SKU 关联；
- 1688 采购下单；
- 密文收货信息传递；
- 供应商发货后物流单号回填；
- 售后和退款状态同步。

这条路线使用现成平台服务，不要求 STEAMx 达到 1688 ISV 解决方案的运营门槛。订购前必须在平台服务市场核对工具的授权范围、隐私处理、自动付款方式、服务费用和退款能力，不使用外部破解版或不明浏览器插件。

## STEAMx 与外部店铺的关系

STEAMx 不直接把抖店或微信小店的完整收银台嵌进 Next.js 页面。平台店铺拥有自己的登录、支付、用户授权和风控体系，直接 iframe 嵌入不可控，也不利于订单归属和售后处理。

STEAMx 可以提供渠道入口：

```text
STEAMx 商品页
    -> 微信购买：微信小店/小程序链接或二维码
    -> 抖音购买：抖店/抖音小程序链接
    -> STEAMx 购买：本站商城订单
```

如果以后需要更统一的品牌体验，可以开发一个微信或抖音小程序展示层，展示 STEAMx 的商品内容，再跳转到平台店铺交易。这是“平台容器承载 STEAMx 内容”，不是把平台收银台随意嵌入 STEAMx 网站。

## 明确不做

- 不申请 1688“铺货分销”插件应用来服务其他商家；
- 不为低订单量自建 1688 ISV 分销平台；
- 不把 `1688-cli` 浏览器自动化当作正式无人值守履约方案；
- 不在未确认当前接口权限和订单协议前启用旧的 `alibaba.trade.fastCreateOrder`；
- 不把抖店或微信小店页面直接当作普通 iframe 组件嵌入。
