# 自然观察功能产品规划

## 一、背景

当前平台已经具备 `项目（project）`、`挑战（challenge）`、`作品提交` 等核心能力，适合承载 STEAM 项目学习流程。

如果要扩展到“自然观察”场景，比如鸟类观察、植物观察、昆虫观察，仅使用现有的项目和完成记录结构还不够。因为自然观察除了“做一个项目”，还会产生大量与“物种、地点、时间、行为”有关的信息。

例如，用户会提出这样的需求：

- 我想找“绿头鸭”相关内容
- 我想知道最近有人在哪里观察到绿头鸭
- 我想看这个物种通常出现在什么环境
- 我想参与一个以“春季迁徙”为主题的观察活动
- 我想在项目里学习怎么观察，并把自己的观察结果发出来

这些需求说明，自然观察不是单一页面的问题，而是一套新的内容关系。

## 二、产品目标

自然观察功能希望同时满足四类需求：

1. 活动参与
2. 项目学习
3. 物种检索
4. 观察沉淀

具体来说，用户应该能够：

- 从挑战页进入一个自然观察主题活动
- 从项目页学习具体观察方法
- 从物种页查找某个具体物种
- 从地图上查看“哪里有人观察到了什么”
- 上传自己的观察记录并形成长期积累

## 三、核心产品结论

自然观察功能建议拆成四层：

1. 挑战层（Challenge）
2. 项目层（Project）
3. 物种层（Species）
4. 观察记录层（Observation Event）

这四层分别回答不同问题：

- 挑战层回答：`为什么做`
- 项目层回答：`怎么做`
- 物种层回答：`这是什么、哪里有`
- 观察记录层回答：`谁在什么时候、什么地方看到了什么`

这四层不是互相替代的关系，而是互相补充的关系。

## 四、四层角色定义

### 1. Challenge：活动主题层

挑战适合作为自然观察活动的上层入口。

它更适合承载：

- 活动主题
- 时间范围
- 参与规则
- 奖励机制
- 情境故事
- 驱动问题
- 推荐项目方向

例如：

- 春季迁徙鸟类观察挑战
- 校园常见生物观察挑战
- 北京城市湿地自然观察月

挑战页的重点不是展示某一个物种，也不是详细记录某次观察，而是组织一个活动主题，把用户带入任务情境。

一句话理解：

**挑战是活动容器。**

### 2. Project：内容承载层

项目适合作为“观察任务模板”或“学习任务页”。

它更适合承载：

- 项目介绍
- 所需材料
- 观察步骤
- 推荐观察点
- 地图模块
- 上传作品入口
- 作品墙

例如：

- 北京公园常见水鸟观察
- 校园鸟类观察路线设计
- 本地鸟类多样性调查

项目页的重点是告诉用户：

- 这件事要怎么做
- 需要什么准备
- 可以去哪儿看
- 看完之后怎么上传成果

一句话理解：

**项目是内容和方法的承载页。**

### 3. Species：物种检索层

物种页是自然观察体系里非常关键的一层。

它适合承载：

- 物种名称
- 学名
- 常见别名
- 识别特征
- 常见栖息环境
- 地图分布
- 最近观察记录
- 相关项目
- 相关挑战

例如：

- 绿头鸭
- 白鹭
- 普通鸬鹚

如果用户想找“绿头鸭”，理想路径不应该是去项目正文里全文搜索，而应该直接进入“绿头鸭”这个物种页。

物种页应该回答：

- 绿头鸭是什么
- 绿头鸭通常在哪儿出现
- 最近谁在哪儿看到了绿头鸭
- 如果我也想观察绿头鸭，我可以参与哪个项目或挑战

一句话理解：

**物种页是自然观察的检索入口。**

### 4. Observation Event：观察记录层

观察记录是最贴近真实世界的数据层。

它适合承载：

- 观察时间
- 观察地点
- 地图坐标
- 照片 / 视频
- 观察到的物种
- 数量
- 行为
- 补充说明
- 是否公开
- 位置精度
- 所属项目
- 所属挑战

例如：

- 2026-03-26 07:20 在奥森南园湿地观察到绿头鸭 6 只，行为为觅食和梳羽

这一层是后面地图、搜索、统计和推荐的基础。

一句话理解：

**观察记录是自然观察的事实数据。**

## 五、四层之间的关系

自然观察功能的核心不是单个页面，而是这些内容之间如何互相连接。

推荐关系如下：

- 一个挑战可以组织多个项目方向
- 一个项目可以独立存在，也可以属于某个挑战
- 一个物种会出现在很多条观察记录里
- 一条观察记录可以关联一个项目
- 一条观察记录也可以间接关联某个挑战
- 一个项目可以积累很多观察记录
- 一个物种页可以聚合多个项目和多个挑战下的记录

举例说明：

### 示例：绿头鸭

用户搜索“绿头鸭”后，进入物种页，可以看到：

- 最近观察记录
- 地图分布
- 哪些项目里常出现绿头鸭
- 哪个挑战正在鼓励用户观察它

其中某条记录可能是：

- 用户 A
- 在奥森南园湿地
- 观察到绿头鸭 6 只
- 行为为觅食、梳羽
- 这条记录属于项目“北京公园常见水鸟观察”
- 该项目又属于“春季迁徙鸟类观察挑战”

这时用户就能形成一条完整路径：

`物种 -> 观察记录 -> 项目 -> 挑战`

这条链路是自然观察产品体验最重要的部分。

## 六、为什么现有结构还不够

当前平台已经有：

- 项目
- 挑战
- 完成记录 / 作品证明

但这些结构仍然偏向“项目学习”和“作品展示”，不够支持自然观察中的“物种”和“观察事实”。

原因主要有三个：

### 1. 物种缺少独立入口

现在如果用户想找“绿头鸭”，平台里没有一个天然的物种页可以承载它。

这会导致：

- 搜索结果分散
- 很难聚合地图分布
- 很难形成长期的物种知识页

### 2. 观察记录不够结构化

当前作品提交更像“上传成果”，而不是“记录一次观察事件”。

自然观察需要明确的结构化信息：

- 观察地点
- 观察时间
- 物种
- 数量
- 行为
- 环境

如果这些信息都只写在备注里，后续很难支持搜索、统计和地图筛选。

### 3. 项目和挑战都不能替代物种层

项目擅长承载方法，挑战擅长承载活动，但它们都不适合直接承担“物种知识页”的角色。

所以物种层必须单独存在。

## 七、页面职责建议

### 1. 挑战页

挑战页应该更偏活动组织。

重点内容：

- 主题
- 时间
- 规则
- 奖励
- 驱动问题
- 推荐项目方向
- 挑战作品展示

### 2. 项目页

项目页应该更偏方法学习。

重点内容：

- 项目介绍
- 材料
- 步骤
- 推荐观察点
- 上传观察成果
- 项目作品墙

### 3. 物种页

物种页应该更偏检索和聚合。

重点内容：

- 物种介绍
- 地图分布
- 最近观察记录
- 相关项目
- 相关挑战

### 4. 观察记录详情

观察记录详情可以先不做成单独一级公开页面，也可以先作为：

- 项目页作品卡片
- 物种页记录卡片
- 地图点位弹层
- 详情弹窗

后续如果记录量足够大，再考虑独立详情页。

## 八、物种页应该放在哪里

结合当前平台导航结构，物种页最适合放在“探索”体系里，而不是“社区”里。

推荐放置方式：

- `/explore/species`
- `/explore/species/[slug]`

原因：

### 1. 物种是可探索内容，不是社区活动

挑战属于社区活动，所以放在 `community` 下是合理的。

但物种不是活动，它是长期存在的知识对象，更适合放在“探索”域。

### 2. 物种不属于某个单独项目

一个物种可能出现在多个项目中。

例如“绿头鸭”可能同时出现在：

- 北京公园常见水鸟观察
- 本地鸟类多样性调查
- 校园鸟类观察路线设计

所以它不应该挂在某一个项目下面。

### 3. 物种需要独立搜索和聚合

把物种放进 `explore` 里，更符合用户心智：

- 探索项目
- 探索物种
- 探索地图结果

因此，物种页建议作为“探索”的一种新内容类型。

## 九、推荐的用户路径

自然观察功能可以支持多种进入方式：

### 路径 1：从挑战进入

用户先看到活动主题，再进入推荐项目，再提交自己的观察成果。

路径：

`挑战页 -> 项目页 -> 上传观察记录`

### 路径 2：从项目进入

用户先学习怎么观察，再上传自己的观察成果。

路径：

`项目页 -> 上传观察记录 -> 地图 / 作品墙`

### 路径 3：从物种进入

用户先搜索某个物种，再看最近观察记录和地图，最后反查相关项目和挑战。

路径：

`物种页 -> 观察记录 -> 项目页 / 挑战页`

### 路径 4：从地图进入

用户先在地图上看到点位，再点开具体记录，最后回到对应项目和挑战。

路径：

`地图 -> 观察记录 -> 项目页 / 挑战页`

这四条路径最终会汇合成同一套内容体系。

## 十、产品上的一句话总结

这套自然观察结构可以概括为：

- 挑战页负责组织活动
- 项目页负责承载方法
- 物种页负责承载检索
- 观察记录负责承载真实世界数据

只有这样，平台才能同时满足：

- 活动运营
- 内容沉淀
- 物种检索
- 地图展示
- 用户参与

## 十一、后续建议

建议下一步按以下顺序推进：

1. 先确认这套信息架构是否接受
2. 再确认页面路由和导航放置
3. 再设计物种与观察记录的数据模型
4. 最后决定第一阶段先上线哪些能力

如果分阶段做，建议优先级如下：

### 第一阶段

- 保留 challenge / project 现有能力
- 增加物种页原型
- 增加观察记录的基础结构
- 支持地图选点和物种关联

### 第二阶段

- 支持物种页检索
- 支持物种地图聚合
- 支持“相关项目 / 相关挑战”联动
- 支持更细粒度的行为标签和统计

### 第三阶段

- 支持 PDF 批量导入物种资料
- 支持推荐观察点
- 支持热力图、季节分布和趋势分析
