# 登录、手机认证与短信配置

核对：2026-10-13，`0d322eda40dfdf81c7feb4f37703c9b38bea2b15`。本文统一维护公开登录、认证提供商和短信配置；管理员建号见 [管理接口](custom-sms-and-manual-users.md)。本次未读取生产凭据、发送短信或验证真实账号。

## 用户入口与兼容能力

登录页和弹层共用 `components/auth/auth-flow.tsx`，提供“验证码登录”和“密码登录”，默认验证码，前台标签和提示以手机号为主。未注册手机号在验证成功后注册；验证码登录后可到账号安全设置密码，密码登录不发送短信或新建账号。

内部邮箱账号仍有兼容能力：密码分支识别含 `@` 的标识，调用邮箱密码认证；否则按手机号认证。它不是专门的公开邮箱注册/登录入口，也不能据此声称邮箱账号必然具备手机号或其他互动资格。管理员测试账号的实际使用方式和限制见 [管理员建号](custom-sms-and-manual-users.md)。

切换方式保留手机号和重发倒计时；未勾选协议时先显示服务条款与隐私确认，明确同意后才继续原操作一次。取消不发请求。找回手机密码通过一次短信验证进入账号安全页，设置成功后返回；失败不自动重试或跳转。历史邮箱找回兼容能力不作为公众入口推广。

## 认证提供商与发送渠道是两层配置

`AUTH_PHONE_PROVIDER` 在服务端选择认证流程。仅明确设为 `supabase` 时采用原生 Phone；其他值按代码使用 legacy，缺省不是“当前生产已选择 legacy”的证据。

| 认证流程 | 发送和校验 |
|---|---|
| `legacy` | 应用生成、保存并消费 OTP；网站服务器发送短信；Supabase 保留用户和会话 |
| `supabase` | 原生 Phone 管理发送、验证、有效期及会话；失败不静默回退到 legacy |

`SMS_PROVIDER` 只影响 legacy 的发送渠道，不选择原生认证。`lib/sms/send.ts` 的优先级是：阿里云两项密钥齐备优先走阿里云；否则显式 custom 且 URL 存在才走自定义 HTTP；缺配置的开发环境才可回退日志模式，生产报错。**不能把 `SMS_PROVIDER=log` 当成覆盖已配置阿里云密钥的“绝不发短信”开关。**隔离测试应使用替身且不注入真实发送凭据。

## legacy 配置

| 配置 | 用途 |
|---|---|
| `SMS_ALIYUN_ACCESS_KEY_ID`、`SMS_ALIYUN_ACCESS_KEY_SECRET` | 阿里云普通短信 Dysmsapi SendSms 凭据 |
| `SMS_PROVIDER=custom`、`SMS_CUSTOM_URL` | 无阿里云配置时使用自定义发送接口 |
| `SMS_CUSTOM_HEADERS` | 可选 JSON 请求头；仅服务端保存 |

签名、模板及变量以 `lib/sms/aliyun.ts` 为准，不在多份文档重复保存实际模板值。普通短信 Dysmsapi 与旧号码认证 Dypnsapi 配置不能混用；应用不调用旧号码认证来消费本地 OTP。发送受理成功不等于手机收到。

custom 接口接收包含 `phone`、`code` 的 JSON POST，手机号按 E.164 格式。不得在日志或前端暴露验证码和发送凭据。

开发配置放 `.env.local`；生产运行配置在服务器 `/opt/steam-app/.env.production`。本地同名生产文件、GitHub 中的 secret 不会自动同步为该运行文件。变更变量和新代码必须匹配，按 [部署流程](deployment.md) 重建相应容器，不能把普通 restart 当成新环境配置已应用。

## 验证、会话和资料

共用接口是 `/api/auth/sms/send` 和 `/api/auth/sms/verify`。legacy 的 `phone_otps`、`phone_to_user` 由服务端访问；原生流程沿用同一用户 ID 并维护兼容映射，不为切换提供商删除用户或重导账号。

前端验证码成功后的会话处理顺序为：优先 `session` 调用 `setSession`；其次 `tokenHash` 调用 `verifyOtp({ type: 'magiclink' })`；最后才使用校验过协议的 `redirectUrl`。旧说明中的“优先跳转，token 用 email 类型”不再沿用。新注册与旧账号、找回密码各按安全站内回跳规则处理，不把任意 Origin 或返回 URL 直接当可信目的地。

首次绑定手机号与普通登录分开验收。原生首次绑定使用 `updateUser({ phone })` 与 `phone_change` OTP；legacy 使用共用 SMS API 的对应类型。当前不由本文增加换绑/解绑能力。资料触发器及缺失补建见 [注册资料补建](ensure-profile.md)，不能把一次建号成功当成所有资料均完整。

## 原生 Phone 切换前核对

在目标实例配置实际可用的提供商、签名、模板、验证长度、间隔和有效期，并保持短信验证开启。原生模板语法与发送商模板语法分开核对；不要把 legacy 的验证码有效期套到原生设置。

核对 `phone_to_user.phone` 与 `auth.users.phone`、用户 ID 及 legacy 会话兼容字段，防止创建重复账号；原生发送失败也可能留下未确认账号，不能直接删用户处理。真实新注册、旧账号资料/作品、退出重登、首次绑定及找回密码均需在授权环境验收后再记录切换完成。

提供商切换前后的服务器变量、应用镜像、发送受理记录和真实收码结果分别记录。历史 9 月的开关、超时和运营商状态只对当时成立，不写成当前配置。

## 排障与证据

区分前端请求、应用接口、Auth 服务、短信受理和运营商送达；记录时间、请求 ID、耗时和错误码，隐藏手机号及敏感响应。控制台无记录不能单独证明网络或运营商故障，容器健康也不能证明短信送达。

不得以自动确认手机号、静默降级、反复重发或单纯加大超时代替根因定位。迁移和建表规则见 [数据库连接与迁移](database-psql.md)，不在短信指南里要求无范围的 `db:push`。
