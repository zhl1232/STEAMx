# 信任等级与内容访问控制方案

> 状态：规划中，尚未实现。最后复核：2026-07-30。
>
> 本方案借鉴社区信任等级的渐进开放思路，但不照搬 Linux.do 的名称、阈值或权限。这里的规则围绕学习内容、青少年安全和现有 STEAM 产品结构设计。
>
> 对应开发设计见 [`TRUST_LEVEL_AND_CONTENT_ACCESS_IMPLEMENTATION.md`](./TRUST_LEVEL_AND_CONTENT_ACCESS_IMPLEMENTATION.md)。

## 1. 背景与目标

当前大多数已发布课程、项目、挑战和学习资料都可以直接读取，登录后的投稿、评论和私信也缺少统一的成长门槛。XP 等级主要承担激励和展示，但部分页面又把它当作权限依据，继续扩展会把“刷经验”“付费会员”“运营角色”和“社区可信度”混成一套不可审计的规则。

本方案的目标是：

- 新增独立的 T0-T4 信任等级，渐进开放内容阅读和社区操作。
- 让课程、项目、挑战和资料逐条显式配置最低阅读等级，不按难度自动推导。
- 保持目录、封面和简介公开，让未解锁用户仍能发现内容并理解解锁条件。
- 让所有正文、资源和写操作都由服务端统一判定，前端锁态只负责反馈。
- 让自动晋升、人工授予、违规限制、历史回算和会员旁路都有可审计记录。

## 2. 当前系统与 P0 风险

### 2.1 XP 可以被客户端驱动

`POST /api/xp/increment` 当前允许任意登录用户提交 `1..1000` 的 XP 增量，速率限制为每分钟 20 次。客户端 `GamificationContext.addXp` 还存在自行提供 `action_type`、`resource_id` 和 `xp_amount` 的流水写入路径。速率限制和客户端去重都不是奖励授权，XP 在完成以下治理前不能作为任何安全权限依据：

1. 删除或禁用通用 XP 自增入口，撤销客户端直接构造 XP 流水的能力。
2. 奖励只允许由服务端白名单业务事件触发，例如审核通过作品、签到结算或挑战结算。
3. 在同一数据库事务内写幂等流水并更新 XP，幂等键由服务端生成，客户端不能指定奖励金额。
4. 审计异常 XP 流水；不把历史 XP 映射成信任等级，也不以清理 XP 作为本方案前置迁移手段。

### 2.2 XP 等级存在多套读取口径

多数页面按 `floor(sqrt(xp / 100)) + 1` 动态计算 XP Lv.，评论图片门槛和部分商店逻辑却读取可能不同步的 `profiles.level`。现有等级说明中如果包含评论发图、额外曝光或社区自治等权益，也会与新信任权限发生冲突。

P0 需要先建立唯一的 XP 等级计算函数，并把 XP Lv. 限定为成长展示、徽章和经济激励。评论、投稿、发帖、私信和受限内容不得再读取 XP 或 `profiles.level` 决策。

### 2.3 摘要和正文位于同一数据行

当前数据结构中：

- `course_lessons` 同一行包含标题以及 `content`、`steps`、`resources`。
- `challenges` 同一行包含列表摘要以及 `scenario`、`resources`、`stages`。
- `learning_resources` 同一行包含 `summary` 和 `content_md`。
- 项目正文还可能分散在 `projects`、`project_materials` 和 `project_steps`。

Postgres RLS 只能决定一行是否可见，不能在同一行中只公开摘要、隐藏正文。因此不能只给现有表增加 `min_trust_level` 后继续 `select *`。实施时必须提供严格投影的公开摘要 RPC/View，并撤销匿名和普通登录用户对受保护正文表的直接读取；正文由统一鉴权 RPC 或受保护 API 返回。

### 2.4 现有写操作缺少统一门禁

当前创建项目、发布评论和发送私信主要只要求登录，评论图片还单独读取 XP 等级。新方案需要将这些散落规则统一为信任能力检查。历史低等级用户仍可查看、编辑或删除自己已经创建的内容，但是否可以新建内容要按当前信任等级判断。

### 2.5 缺少统一的违规与限制事实

T1 的“无有效限制”以及 T2/T3 的“近期无确认违规”目前没有完整、统一的数据源。上线前需要建立确认状态、有效期、处理人、申诉/撤销和信任影响记录；不能用未处理举报直接降级，也不能默认所有历史用户都有完整的无违规记录。

## 3. 四条独立轴

| 轴 | 回答的问题 | 主要数据 | 不得承担的职责 |
|---|---|---|---|
| XP Lv. | 用户完成了多少受奖励行为 | `profiles.xp`、XP 流水 | 内容权限、社区安全判断 |
| Trust T0-T4 | 用户是否具备稳定、可信的参与记录 | 信任状态、活动事实、审核贡献、违规记录 | 付费权益、后台角色 |
| Membership | 用户是否拥有有效订阅权益 | `membership_tier`、`membership_period`、有效期 | 投稿、评论、发帖、私信或审核权限 |
| Role | 用户是否承担特定运营职责 | `profiles.role`：`user/teacher/moderator/admin` | 普通成长等级；T4 也不自动获得角色 |

四条轴不能互相写回。XP 增长不提升 Trust，购买会员不提升 Trust，T4 不成为审核员，角色变化也不改写 XP。

## 4. 信任等级定义

等级名称是产品文案占位，实施时可以调整名称，但编号和规则需要稳定。

| 等级 | 暂定名称 | 晋升方式 | 条件 |
|---|---|---|---|
| T0 | 新成员 | 注册后默认 | 已登录但尚未满足 T1；可阅读有权限的内容并完成个人学习，不可公开投稿或互动 |
| T1 | 参与者 | 自动 | 账号满 1 天、至少 2 个有效活跃日、完成年龄确认、无有效账号限制 |
| T2 | 贡献者 | 自动 | 满足 T1；账号满 7 天、至少 5 个有效活跃日、至少 3 项审核通过贡献、至少 5 条有效评论/回复、近 30 天无确认违规 |
| T3 | 核心成员 | 自动 | 满足 T2；账号满 30 天、至少 15 个有效活跃日、至少 10 项审核通过贡献且覆盖至少两个模块、至少 20 条有效评论/回复、近 90 天无确认违规 |
| T4 | 受信任成员 | 人工 | 当前为 T3，由管理员人工授予并填写原因；可撤销，不能由任务或 XP 自动获得 |

### 4.1 v1 能力边界

- T1 解锁投稿、评论和回复。
- T2 解锁独立发帖和发起私信。
- T3 与 T4 在 v1 不额外获得写操作或更高接口限额，只用于对应等级内容阅读和信任标识。
- 所有等级继续受相同的内容审核、频率限制、敏感词、安全和隐私规则约束。
- v1 不因单纯长期未登录而自动降级；确认违规可以触发写入冻结、信任等级上限或人工降级。

### 4.2 指标口径

**有效活跃日**

- 以 `Asia/Shanghai` 自然日去重，同一用户每天最多记 1 天。
- 只接受服务端白名单事件，例如完成/保存有效课时进度、完成一局可验证游戏、提交待审作品、产生有效评论或完成一次审核通过的自然观察。
- 单纯登录、刷新、浏览页面、客户端自报事件不计入。

**审核通过贡献**

- 模块枚举固定为 `projects`、`course_works`、`challenges`、`nature_observations`。
- 可计入审核通过的原创项目、`completed_projects.status='approved' AND record_kind='final'` 的课程作品、审核通过的挑战投稿，以及符合当前点亮口径的审核通过自然观察。
- 同一底层作品被项目、挑战或完成记录重复引用时只计一次；系统/运营账号的自动内容不计。
- 普通删除或不活跃不触发自动降级；因作弊、侵权或审核撤销失效时，转成确认违规或人工复核事件处理。

**有效评论/回复**

- 只统计未删除、未被确认违规、非系统账号发布的评论和回复。
- 同一内容下短时间重复文本、被反垃圾规则合并的记录只计一次。
- 计数用于晋级，不直接产生 Trust 分数，避免通过大量低质量互动线性刷级。

**年龄确认**

- 现有 `profiles.age_confirmed_at` 只能作为待清理兼容字段；新增明确的年龄确认事实、确认方式和来源证据，Trust 不直接读取旧字段，也不能把 `birth_date` 非空视为已经确认。
- 当前注册 trigger 和短信验证链路会自动写 `age_confirmed_at`，这些旧值只代表“账号流程经过”，不证明本人/监护人完成了年龄确认，迁移时一律不得直接满足 T1。
- 具体是本人确认、监护人确认还是管理员录入，应由账号安全流程记录并可审计。
- 缺少年龄确认的历史用户可以管理已有内容，但在完成确认前不能晋升 T1 或执行新的受限写操作。

### 4.3 评估与状态优先级

- T1-T3 在白名单事实变化后异步评估，并由每日任务兜底；同一规则版本和事实快照必须幂等。
- `automatic_level` 只取 0-3；T4 记录为独立的管理员授予。
- 有效等级建议按 `min(T4 人工授予或 automatic_level, 有效违规等级上限)` 计算。
- 写入冻结独立于等级：冻结期内保留必要的内容阅读和本人内容管理，但禁止新增投稿、评论、发帖和私信。
- 所有晋升、冻结、上限、人工授予、撤销和到期恢复都写入不可由用户修改的审计日志，并记录规则版本和指标快照。

## 5. 内容访问模型

### 5.1 每项内容显式配置

课程、项目、挑战和学习资料都需要以下访问字段：

| 字段 | 建议值 | 说明 |
|---|---|---|
| `access_scope` | `public/authenticated/trust` | 区分完全公开、登录可读和按信任等级读取，避免 T0 同时表示匿名 |
| `min_trust_level` | `0..4` | 仅 `trust` 范围使用；由编辑明确选择，不从难度、标签或 XP 推导 |
| `member_read_bypass` | boolean | 普通已发布内容默认允许有效会员旁路；安全或特殊内容可显式关闭 |

课时在 v1 完全继承所属课程的访问策略，不提供课时级覆盖，避免课程目录显示可读但某个课时意外锁定。新内容发布前必须完成访问配置；缺失策略时正文判定应失败关闭并告警，不能静默当作公开。

历史内容迁移时先显式回填 `public` 以保持当前可见性，再由运营逐条调整。这样既保留“逐内容配置”，也避免迁移瞬间把全部内容锁死。

### 5.2 阅读矩阵

| 内容状态 | 匿名 | T0 | T1 | T2 | T3 | T4 | 有效会员 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 目录、封面、简介 | 可读 | 可读 | 可读 | 可读 | 可读 | 可读 | 可读 |
| `public` 正文 | 可读 | 可读 | 可读 | 可读 | 可读 | 可读 | 可读 |
| `authenticated` 正文 | 登录后 | 可读 | 可读 | 可读 | 可读 | 可读 | 可读 |
| 最低 T1 正文 | 不可读 | 不可读 | 可读 | 可读 | 可读 | 可读 | 可旁路 |
| 最低 T2 正文 | 不可读 | 不可读 | 不可读 | 可读 | 可读 | 可读 | 可旁路 |
| 最低 T3 正文 | 不可读 | 不可读 | 不可读 | 不可读 | 可读 | 可读 | 可旁路 |
| 最低 T4 正文 | 不可读 | 不可读 | 不可读 | 不可读 | 不可读 | 可读 | 可旁路 |
| 草稿、私有或角色专属内容 | 不可读 | 不可读 | 不可读 | 不可读 | 不可读 | 不因 T4 可读 | 不可旁路 |

“会员可旁路”只适用于 `member_read_bypass=true` 的已发布普通正文和附件。会员过期瞬间按现有 membership helper 重新判定；`founder/lifetime` 按现有长期有效语义处理，`monthly/yearly` 必须检查过期时间。

### 5.3 社区操作矩阵

| 操作 | 匿名 | T0 | T1 | T2 | T3 | T4 | 会员旁路 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 浏览公开摘要 | 是 | 是 | 是 | 是 | 是 | 是 | 不需要 |
| 点赞、收藏、关注 | 否 | 是 | 是 | 是 | 是 | 是 | 否 |
| 完成可读课程/项目的个人进度 | 否 | 是 | 是 | 是 | 是 | 是 | 否 |
| 课程作品、项目完成证明、挑战投稿、自然观察投稿 | 否 | 否 | 是 | 是 | 是 | 是 | 否 |
| 评论和回复 | 否 | 否 | 是 | 是 | 是 | 是 | 否 |
| 独立创建公开项目/社区帖子 | 否 | 否 | 否 | 是 | 是 | 是 | 否 |
| 发起私信 | 否 | 否 | 否 | 是 | 是 | 是 | 否 |
| 审核、后台管理 | 否 | 否 | 否 | 否 | 否 | 否 | 否 |

接收私信仍服从接收方隐私设置。已经存在的对话是否允许 T0/T1 回复，v1 统一按“发送私信”处理并要求 T2，避免通过旧线程绕过门槛。

## 6. 作者、会员与角色旁路

访问判定必须逐项明确，不能使用笼统的 `isStaff` 全站放行：

| 身份 | 阅读旁路 | 写操作旁路 |
|---|---|---|
| 内容作者 | 可预览并管理本人草稿和已发布正文 | 可编辑/删除本人已有内容；创建新内容仍按 Trust 门槛 |
| Teacher | 仅对明确分配的课程/挑战获得阅读和教学管理权限 | 仅执行分配范围内的教学操作；个人投稿、评论、发帖、私信仍按 Trust |
| Moderator | 为审核、举报处理读取相关受限内容 | 仅旁路审核/处置操作，不旁路个人社区行为 |
| Admin | 可读取和配置全部内容及访问策略 | 可执行后台管理；以普通用户身份发言时仍记录真实账号和审计来源 |
| 有效会员 | 仅旁路允许会员旁路的已发布正文阅读 | 无写操作旁路 |
| T4 | 读取 T4 及以下内容 | 不获得审核、配置、教师或后台权限 |

如未来支持协作作者，必须通过明确的内容成员关系授予，不能仅凭角色或关注关系推断。

## 7. 统一访问判定与数据保护

### 7.1 确定性判定顺序

完整正文读取按以下顺序判定：

1. 内容不存在、草稿或私有且访问者没有明确的作者/分配/审核权限：返回 404。
2. 访问者是内容作者、被分配教师、处理该内容的审核员或管理员：按对应职责放行。
3. 账号存在禁止阅读的安全限制：拒绝；普通写入冻结不会自动剥夺已获阅读权。
4. `access_scope=public`：放行。
5. 未登录：返回 401；`access_scope=authenticated`：登录后放行。
6. 有效会员且该内容允许会员旁路：放行。
7. 有效 Trust 等级达到 `min_trust_level`：放行；否则返回结构化 403。

统一 SQL 判定函数不得接受客户端可伪造的 `user_id`；普通请求从 `auth.uid()` 读取身份。确需 service role 的后台任务必须先验证真实操作人，再调用仅服务端可用的判定入口并写审计。

### 7.2 摘要与正文分层

v1 推荐采用以下过渡结构：

- 为四类内容提供严格列白名单的 catalog RPC/View，只返回 `id/title/cover/summary/tags/status/access_scope/min_trust_level` 等摘要字段，禁止 `select *`。
- 撤销 anon/authenticated 对含正文 base table 的直接 SELECT；允许阅读正文的用户通过固定 `search_path` 的受控 RPC 或服务端 API 获取。
- 受保护的子表、课时步骤、材料、资源列表使用同一内容判定，不能只锁主表。
- 所有 service-role API、RSC 数据加载和 AI Tutor 上下文都必须显式调用统一 checker；service role 会绕过 RLS，不能把 RLS 当成这类代码的兜底。
- 搜索、推荐、站点地图、metadata、JSON-LD、日志和 RSC Flight payload 只能使用公开摘要，不能把锁定正文预取到浏览器后再隐藏。

如果后续正文结构继续变复杂，再把正文拆到独立受保护表；在完成拆分前，上述 RPC 投影是上线门槛。

### 7.3 附件和缓存

- 锁定内容的 PDF、视频、课件、源码和原图必须进入私有存储，或通过鉴权后生成短时签名 URL；公开 OSS URL 无法靠隐藏按钮保护。
- catalog 响应不得包含原始附件地址，签名接口必须再次检查正文阅读权限。
- 受用户 Trust、会员或角色影响的正文响应不得进入跨用户共享缓存，至少使用私有缓存或 `no-store`。
- 锁定详情页可以渲染公开摘要；浏览器网络响应、HTML 和 RSC payload 中都不得出现正文片段。

### 7.4 API 错误契约

建议统一返回以下 reason code：

| HTTP | code | 用途 |
|---|---|---|
| 401 | `AUTH_REQUIRED` | 正文或操作需要登录 |
| 403 | `TRUST_LEVEL_REQUIRED` | 返回当前等级、最低等级及是否可用会员阅读旁路，不返回正文 |
| 403 | `ACCOUNT_RESTRICTED` | 账号冻结或限制阻止当前操作 |
| 403 | `MEMBERSHIP_REQUIRED` | 仅在未来存在明确会员专属内容时使用，不与 Trust 混写 |
| 404 | `CONTENT_NOT_FOUND` | 内容不存在，或草稿/私有内容对当前用户不可见 |

前端锁态根据 code 展示原因和下一步，但不能自行计算后放行。

## 8. 建议数据模型

以下是实施方向，不代表本轮已经创建数据库结构：

**`user_trust_state`**

- `user_id`、`automatic_level`、`manual_grant_level`、`effective_level`。
- `level_cap`、`write_frozen_until`、`rule_version`、`evaluated_at`。
- T4 只通过 `manual_grant_level=4` 表达，并要求授予时自动等级为 T3。

**`trust_level_audit`**

- 记录变更前后等级、事件类型、规则版本、原因、指标快照、操作人和时间。
- 客户端无写权限；自动评估、管理员操作和限制到期都必须落审计。

**`trust_activity_events`**

- 只接受服务端白名单来源，包含事件类型、来源记录、发生时间和稳定去重键。
- 用于计算活跃日，不复制评论数和贡献数等可从业务表验证的事实。

**`trust_safety_cases` / `user_restrictions`**

- 区分举报、待确认、确认、撤销；记录严重度、确认人、确认时间、有效期和申诉结果。
- 限制记录明确是写入冻结、等级上限还是人工复核，不能由一条未确认举报直接影响等级。

**`user_age_confirmations`**

- 记录确认方式、状态、确认人、条款版本、最小化证据引用、确认/撤销时间；Trust 只认 active 且来源完整的记录。
- 现有注册和短信验证自动写入的 `profiles.age_confirmed_at` 不迁入，不作为 T1 证据。

**`content_teacher_assignments`**

- 用带外键的课程/挑战指派关系表达 Teacher 阅读旁路，记录分配人、原因、时间和撤销状态。
- 没有有效指派关系时，`profiles.role='teacher'` 本身不产生正文旁路。

**内容访问字段**

- 在 `courses`、`projects`、`challenges`、`learning_resources` 上增加 `access_scope`、`min_trust_level` 和 `member_read_bypass`。
- 课时继承课程；发布接口和 Admin 表单必须要求显式配置。

高频查询需要为用户状态、有效限制、贡献状态和内容访问字段补索引，并在真实数据量上保留 `EXPLAIN` 基线。

## 9. 老用户回算与灰度发布

### 9.1 历史回算

1. 固定 `as_of` 时间和 `rule_version`，先 dry-run 输出 T0/T1/T2 人数、每项未满足原因和异常数据。
2. 使用账号创建时间、白名单活跃事实、审核通过贡献和有效评论回算；不读取 XP 作为替代指标。
3. 老用户自动回算最高为 T2；T3/T4 在首轮回算中一律不授予。T3 自动评估要在单独灰度阶段开启，避免下一轮任务立即绕过 T2 上限。
4. 可迁移的历史确认违规先归一化；缺少历史安全数据时可为 T0-T2 记录一次“仅已知记录范围内无违规”的迁移假设，但不能据此授予 T3。
5. 缺少新的可信年龄确认事实时不从旧 `age_confirmed_at` 或 `birth_date` 推断，用户完成显式确认后再重评；本人已有内容的管理权继续保留。
6. 写入使用稳定幂等键并保留完整审计；不追扣或重算历史 XP。

### 9.2 发布顺序

1. **P0 奖励治理**：关闭任意 XP 自增和客户端流水写入，统一 XP Lv. 口径。
2. **信任事实层**：新增状态、活动、违规、年龄确认和审计结构，只计算不拦截；年龄确认入口未上线前不得启用 T1 写操作门禁。
3. **策略字段与回填**：以 additive migration 增加访问字段，所有历史已发布内容显式回填为当前等价的 `public`；此时只记录策略，不启用门禁。
4. **内容双层读取**：上线摘要 RPC/View、正文 checker 和私有附件链路，新发布内容强制配置策略，并完成直接 Supabase 泄漏测试。
5. **历史回算**：dry-run 审核后幂等写入，用户端先只展示等级和晋级缺口。
6. **影子判定**：记录“如果启用将拒绝”的请求、原因和用户分布，不实际阻断。
7. **逐模块启用**：优先选择少量资料/课程试点，再扩到项目和挑战；API 与 RLS/RPC 同时启用。
8. **社区操作门禁**：依次接入投稿、评论/回复、发帖和私信，观察误拦截后再开放 T3/T4 阶段。

### 9.3 回滚

- 使用按内容类型和操作类型拆分的 feature flag 关闭 Trust enforcement。
- 回滚时把已发布内容恢复到迁移前的显式可见策略，但保留草稿、私有内容和角色边界。
- 不关闭 RLS、不重新授予正文 base table 的公共 SELECT，也不删除审计数据。
- 数据库只做新的 forward migration；按 `.cursor/rules/db-migrations.mdc` 使用 `pnpm db:push`，不使用 `supabase db push`。

## 10. 监控与验收

### 10.1 关键监控

- 各 reason code 的 401/403 数量、内容类型、当前/要求等级分布和误锁申诉率。
- T0-T4 用户数、每日晋升/冻结/人工授予数量、规则版本差异和异常突增。
- 会员阅读旁路次数、会员到期后的拒绝情况，以及任何写操作旁路尝试。
- catalog/正文接口延迟、判定查询耗时、签名资源拒绝和 service-role 未经 checker 的告警。
- 搜索索引、metadata、日志和缓存中的正文泄漏扫描。

### 10.2 必须通过的场景

- 匿名、T0-T4、有效会员、过期会员分别访问四类内容的摘要、正文和附件。
- 内容作者、被分配 Teacher、Moderator 和 Admin 的阅读/管理边界；T4 不能进入审核或后台。
- T0/T1/T2 分别尝试投稿、评论、发帖和私信；会员不能绕过写操作门槛。
- 用户直接调用 Next API、Supabase REST/RPC、猜测附件 URL，结果与页面锁态一致。
- 列表、搜索、metadata、HTML、RSC payload 和浏览器缓存只包含允许公开的字段。
- 会员刚好到期、自动晋升并发、重复评估、冻结/等级上限到期、T4 撤销和角色变化。
- 老用户回算重复执行结果一致，最高 T2；回滚后已发布内容恢复可见，草稿和私有内容仍不可见。
- P0 修复后，客户端无法指定 XP 金额、动作类型或资源 ID 伪造奖励，重复业务事件不重复记账。

## 11. 非目标

- 不用 Trust 替换 XP、会员、角色、徽章或金币系统。
- 不按内容难度、年龄标签或 XP 自动推导最低信任等级。
- v1 不提供因单纯不活跃而自动降级，也不自动授予 T4。
- v1 不按 T3/T4 提高发帖或私信限额；限流仍是独立的反滥用机制。
- 不承诺 DRM；已授权用户仍可能复制内容，本方案解决的是平台访问控制和意外泄漏。
- 不在首次发布中一次性锁定全部历史内容，先完成可观测、可回滚的灰度验证。

## 12. 实施文档同步要求

本文只记录规划。后续真正增加路由、共享鉴权模块、数据库结构或关键行为时，需要在同一变更中更新 `PROJECT_INDEX.md`；数据库迁移必须走项目规定的 forward migration 和 `pnpm db:push` 流程。
