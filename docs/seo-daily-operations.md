# SEO / GEO 日常检查与专题运营

适用站点：创探空间，`https://steam.bj.cn`。主词使用「创探空间」，页面标题和正文按实际内容使用「少儿 STEAM」「积木搭建」「Scratch 入门」「科学实验」。本手册是操作流程，不代表已获得任何搜索后台权限或收录、排名结果。

## 1. 交接与首次设置

指定一位运营负责人记录数据、一位开发负责人处理抓取异常。首次按 [索引清单](seo-indexing-checklist.md) 完成 Google Search Console、百度搜索资源平台、Bing Webmaster Tools 的站点验证，各自提交 `https://steam.bj.cn/sitemap.xml`。旧域的验证不能代替新域验证；验证码和 API token 不写进报表或提交仓库。

本次代码增加的入口需部署后再检查：

| 专题 | 规范页面 | 内容职责 |
|---|---|---|
| 积木搭建 | `/learn/blocks` | 材料准备、结构与稳定性、搭建尝试、复盘，以及已发布积木课程 |
| Scratch 入门 | `/learn/scratch` | 事件、动作、重复与调试，从小作品开始，链接已发布 Scratch 课程 |
| 科学实验 | `/learn/science` | 提问、预测、比较与观察记录，链接已审核科学项目 |

三个专题由 `/courses` 提供普通链接，同时进入 sitemap 和 llms.txt。正文在服务器输出，不需要登录。课程与项目列表读取已有公开内容；有相应资源才展示，不虚构课程、适用年龄或免费承诺。搜索引擎索引专题页后，家长可继续进入具体课程和项目。

## 2. 每次发布：先跑自动检查

在项目根目录使用 Node.js 22：

```bash
pnpm seo:check --base-url https://steam.bj.cn --report .tmp/seo-report.json
```

也可直接运行 `node scripts/check-seo.mjs --base-url https://steam.bj.cn --report .tmp/seo-report.json`，不需要安装依赖或提供后台 token。脚本只发公开 GET 请求，不提交 URL、不修改数据库。退出码非零表示检查失败，报告写入指定文件。

检查范围：robots、sitemap、首页、课程入口、三个专题，以及 sitemap 中抽样的项目、课程、课时；核对 HTTP 状态、标题、描述、canonical、意外 noindex、正文标题、结构化数据格式与分享图片可访问性。检查爬虫规则是否允许公开页面及图片、是否仍屏蔽私有 API。它是有限抽样，不等于全站抓取、浏览器验收或已被收录。

报告中的 `errors` 需要处理；`warnings` 需要人工判断，例如桌面/手机各有一个 H1、图片经 CDN 重定向、外站图片的 robots 无法由本站规则判断，不会因此直接判为发布失败。脚本每次请求超时 8 秒，网络及服务器临时故障最多重试一次；超时后可稍后重跑。首次本地开发编译较慢，建议预热页面后再运行。

Release workflow 在服务器部署完成后、百度推送前执行相同检查，并保留 `seo-check-<提交 SHA>` JSON artifact 30 天。检查失败会标记发布流程失败并跳过百度推送；**此时应用可能已部署成功，SEO 检查不会自动回滚**。开发先看报告，区分网络瞬断、资源故障和页面回归，再决定修复或回滚。不要因一次外部网络失败立即改代码。

部署后还要人工抽查：

1. 手机和电脑各打开三个专题，确认入门步骤可读、现有课程/项目链接可用。
2. 打开一节积木课和一节 Scratch 课，确认课程内容、步骤与作品入口正常；禁用 JavaScript 时仍能看到本课步骤与提示。
3. 抽查探索列表与自然观察列表：正常后续页应有独立 canonical 和可点击分页链接；不存在的后续页应返回 HTTP 404，数据库故障不能被显示成空列表或“物种不存在”。
4. 在各搜索后台抽检一个专题和一个新发布详情页，记录抓取/索引状态，而不是只看网页能否打开。

### sitemap 故障的处理约定

- sitemap 在请求时生成，完整成功结果使用 Next.js 数据缓存，1 小时后重验证；构建阶段不连接内容数据库。数据查询失败时抛出错误，不再返回只有静态 URL 的 HTTP 200。若有上一次成功缓存，后台重验证失败时可继续使用旧内容；没有成功缓存时应明确失败。缓存是否保留跨部署取决于部署环境，不能假定一定存在。
- 作品 `lastmod` 取有效的完成时间和审核时间中的较晚值，反映审核公开的变化；不能每次请求都写当前时间。
- 脚本要求生产 sitemap 含项目、课程、课时，以及三个专题。若出现数量骤减，对照上一次报告检查查询、审核状态与数据库连通性，不要用伪造 URL 补数。

## 3. 每日：5–10 分钟异常检查

| 检查 | 怎么做 | 发现异常时 |
|---|---|---|
| 技术可访问性 | 执行上面的 `seo:check`；发布当天也可查看 Release artifact | 保存报告、时间、失败 URL 和提交版本，交开发处理 |
| Google | 查看「站点地图」状态、上次读取时间、发现网页数，以及网页索引异常、安全问题或人工处置提示 | 实时测试与站点地图读取结果分别记录；按下面的故障流程处理，不能只凭绿色实时测试判为恢复 |
| 百度 | 查看索引量趋势、抓取异常及平台消息 | 记录异常起点，核对最近部署和新增内容；以当前账号可用工具为准 |
| Bing | 查看索引/抓取错误及站点通知 | 抽检问题 URL，记录平台给出的原因 |
| 当日新内容 | 确认公开链接、正文、材料/步骤、图片、专题归属与站内链接 | 缺内容先补内容；不要批量发布只有标题的专题页 |

技术脚本目前通过手动命令和发布流程运行，**没有额外配置每日定时任务**。低流量阶段不因单日点击或排名波动反复改标题；报表更新有延迟，记录数据覆盖的截止日期。

### Google：实时测试成功，但站点地图仍显示「无法抓取」

这项检查由有后台权限的管理员执行。`pnpm seo:check` 只能检查公开响应，不能读取 Search Console 中的提交、处理及索引状态。各层结果分开记录：

| 检查层 | 通过的证据 | 仍不能据此认定的事项 |
|---|---|---|
| 公开技术检查 | HTTP 200、XML 可解析、规范 URL 和 robots 正常 | Google 已经读取 sitemap |
| Google 实时网址测试 | 测试的是完整 sitemap 地址，「允许抓取＝是」「网页抓取＝成功」 | 常规 sitemap 抓取/解析任务已成功，或所列页面已收录 |
| Google 站点地图报告 | 状态为「成功」、上次读取时间已更新、发现网页数与清单规模相符 | 所有被发现的页面已抓取或收录 |
| 具体内容页索引 | 首页、课程或项目 URL 的索引报告显示已编入索引 | 其他 URL 同样已收录或具有排名 |

实时测试不更新已有索引记录，也不保证随后收录；站点地图报告中的「发现网页」表示解析出的网址数量。[网址检查说明](https://support.google.com/webmasters/answer/9012289?hl=zh-Hans)、[站点地图报告说明](https://support.google.com/webmasters/answer/7451001?hl=zh-Hans)

操作流程：

1. 核对完整地址为 `https://steam.bj.cn/sitemap.xml`，记录后台提交日期、上次读取时间、状态、发现网页数及展开后的错误详情。**提交日期更新不代表读取成功**；字段为空就原样记录为空，不用提交日期填补。列表与详情显示不同则分别记录并核对最新详情。
2. 用「网址检查 → 测试实际网址」检查同一地址，记录测试时间、允许抓取和网页抓取结果。实时测试失败时，将具体错误与技术检查报告交开发定位。
3. 实时测试成功而站点地图仍失败时，可重新提交一次相同 sitemap 地址。若已经重新提交，记录为「实时抓取通过，站点地图读取未确认」，保留错误状态，按约定时间复查。建议当天稍后或次日检查一次；这是内部检查节奏，不是 Google 的处理时限承诺。
4. 复查仍失败、或出现新的错误时，由开发对照测试/提交时段的服务器及网关日志，检查 `/sitemap.xml` 与 `/robots.txt` 的状态码、耗时、连接失败或拦截记录。无源站访问记录时，先核对是否发生了新的抓取尝试，再检查 DNS、TLS 及上游链路；不能仅凭日志缺失断定网络故障，也不能仅凭 User-Agent 或一次本地 200 判断 Google 常规爬虫已可访问。[验证 Google 请求的方法](https://developers.google.com/crawling/docs/crawlers-fetchers/verify-google-requests)
5. 以站点地图报告的新成功记录结束这项故障跟踪；若状态成功但发现网页数仍为 0，对照公开 XML 的实际 URL 数量继续检查解析结果。之后单独跟踪内容页索引。`sitemap.xml` 本身无需点击「请求编入索引」，该操作留给希望出现在搜索结果中的内容页面。

使用 [站点地图检查记录模板](seo-sitemap-check-template.csv)，一行记录「检查时间＋平台＋sitemap URL」；未显示的字段写「空白/未提供」，不要写成成功或推测值。错误详情尚未展开时注明「仅有汇总错误」。Google、百度、Bing 分别记录，缺少的后台功能标记 `N/A`。

本次截图对应的记录示例（用户提供，2026-09-20）：Google 实时测试于 11:39:02 抓取成功；重新提交后的列表显示提交日期 2026-09-20、类型未知、状态「无法抓取」、发现网页 0、上次读取时间空白。**当时仍未确认 sitemap 读取恢复**，不得仅凭实时测试的绿色结果关闭问题。此例只说明记录方法，不代表之后的线上状态。

## 4. 每周：按页面和搜索词记录效果

固定每周同一天检查，默认比较「最近 28 天」和「前 28 天」。不足 56 天的新站保留实际起止日期，不强行计算完整环比。不要混合平台、搜索类型、国家/地区、设备或页面过滤条件。

### Google Search Console

1. 在「网页索引」看已索引/未索引原因；对三个专题及本周新增页面使用「网址检查」。实时测试通过只说明当前可访问，不等于已经进入索引。[索引报告说明](https://support.google.com/webmasters/answer/7440203?hl=zh-Hans)
2. 在「效果 → 搜索结果」选择 Web，设置 28 天对比，记录展示、点击、CTR 和平均排名。
3. 先按页面精确 URL 筛选一个专题，再切到「查询」，导出带来展示/点击的搜索词；课程和项目详情另外记录。专题数据不能直接代表所有相关详情页的数据。
4. 反过来点一个搜索词查看「网页」，确认由哪个页面承接；单独标记品牌词「创探空间」与非品牌词，如「Scratch 入门」。保持相同过滤条件比较。[效果报告](https://support.google.com/webmasters/answer/7576553?hl=zh-Hans)、[过滤与比较](https://support.google.com/webmasters/answer/17011165?hl=en)

### 百度搜索资源平台

1. 在「索引量」看趋势，在账号可用的抓取工具中抽检 URL。索引量表示搜索候选数据库中的规模，不等同点击或精确的逐 URL 收录清单。
2. 在「流量与关键词」记录对应时间的展现、点击和热门关键词；能查看落地页时一并导出。当前账号未提供的逐 URL 状态、CTR、排名等填 `N/A`，不套用 Google 的字段。
3. 检查主动推送结果和 sitemap 抓取状态（如后台有相应权限）。提交成功只是发现信号，不代表收录成功。`site:` 查询仅作辅助，不能据此填写精确收录量。[百度平台使用指南](https://ziyuan.baidu.com/college/articleinfo?id=3329)

### Bing Webmaster Tools

1. 检查 sitemap、URL Inspection / Site Explorer 中可用的索引状态及抓取错误。
2. Search Performance 中记录页面与关键词的展示、点击、CTR、平均位置，优先按 Web 来源与上一周期比较。平均位置的适用来源与 Google 不同，不能跨平台直接平均。[Search Performance 说明](https://www.bing.com/webmasters/help/search-performance-c680da36)
3. 若账号显示 AI Performance，另外记录被引用页面、引用次数及 grounding queries。该报告覆盖 Bing/Microsoft 相关 AI 场景，不等同访问量，也不代表 Google、百度或全网 AI 的引用率。[AI Performance 说明](https://www.bing.com/webmasters/help/ai-performance-9f8e7d6c)

### 记录格式

复制 [周报 CSV 模板](seo-weekly-report-template.csv) 到团队表格。每行是「平台＋时间窗口＋页面＋查询词」的一组观察；页面汇总行的查询词填 `ALL`，不要再与其查询词明细相加。搜索后台可能隐藏少量查询词，明细合计不一定等于总量。

必记：检查日期、平台、统计起止日、来源/过滤条件、专题、规范 URL、发布日期、索引状态/原因、首次观察到已索引日期、查询词、品牌词与否、展示、点击、CTR、平均位置、上期展示/点击、本次变更、负责人、复查日期。无法取得的字段留空或 `N/A`；首次观察到的日期不是搜索引擎真实首次索引时间。

若已有站内分析，再单独看进入课程、开始课时等行为。搜索后台点击不能代替这些行为。本次未接入 GA4、百度统计或新的用户行为采集，也未读取三个平台的私有后台数据。

## 5. 每月：决定先修页面还是扩展主题

| 观察到的信号 | 优先行动 | 下一次看什么 |
|---|---|---|
| 页面未索引且有抓取错误 | 修状态码、robots、canonical、图片/正文可访问性及站内链接 | 修复后网址检查与索引原因是否变化 |
| 可抓取但持续未索引 | 检查是否重复、内容过薄、缺少独立价值；完善具体案例和实操说明 | 是否被发现/索引及首次展示，不承诺时间 |
| 有展示，点击相对同类页面偏低 | 根据真实查询调整标题、摘要和首屏说明，使搜索承诺与页面一致 | 同位置、设备和地区条件下的点击/CTR 趋势 |
| 有明确长尾查询，现有页面只回答了一部分 | 先补当前页的材料、过程、示例与复盘；有独立学习任务时再建新页 | 对应查询是否带来持续展示和访问 |
| 有点击，进入课程或开始学习少 | 若已具备行为数据，检查入口、难度信息、内容匹配和移动端体验 | 实际课程行为，不能从搜索点击猜转化 |
| 某专题持续有需求 | 优先扩展该专题下真实可完成的课程/项目，补回相关内链 | 后续两个周期的页面覆盖、点击与学习行为 |

新页面通常先积累 2–4 周观察记录；这是内部复查节奏，不是收录承诺。样本很少时延长观察，不设统一 CTR 及排名达标线。每轮只记录少量明确改动，避免同时改标题、路径、正文后无法判断原因。已有 URL 尽量稳定；确需改路径时做永久重定向并更新内链与 sitemap。

专题编辑遵循「提出一个问题 → 动手尝试 → 记录差异 → 解释与改进」。内容优先展示真实材料、步骤、作品与观察结果，适用年龄以已审核课程信息为准。科学内容需写清材料与操作边界。GEO 同样依靠清楚、可信、可引用的公开正文；llms.txt 和结构化数据只是辅助，不能承诺 AI 推荐。
