# PBL 挑战指南：内容规范与当前实现

> 本文是 PBL 挑战的当前内容规范和实现入口。历史系统设计、阶段重构过程与旧数据模型不再作为开发依据；当前行为以代码、数据库迁移和审核后台为准。

## 一、挑战的定义

真正的 PBL 挑战不是一句目标口号，也不是一份照做即可的项目教程。它是一份任务书：

`真实任务 + 清晰约束 + 完成标准 + 可选脚手架 + 反思提交`

挑战页至少要回答：

1. 要解决什么问题？
2. 为什么这是值得做的真实任务？
3. 最后要交出什么？
4. 在什么限制下完成？
5. 不会做时可以从哪里补能力？
6. 做完后如何解释方案和迭代过程？

项目教程适合单一技能、明确步骤和可重复复现；主题页适合背景知识、案例合集和对象浏览。挑战应包含多因素取舍、多阶段推进、没有唯一答案的设计测试，以及完整方案、作品或报告的提交。

## 二、最小内容结构

前 5 项是必须项，后 3 项是强烈建议项。

### 1. 情境 / 任务背景

把任务放进真实场景，让用户理解为什么要做。避免只写“做一个桥”，应写成“为 30cm 宽的沟设计一座轻量承重桥”。对应字段：`scenario`。

### 2. 驱动问题

用一个问题说清核心矛盾，并留下方案空间，例如“怎样在材料有限的情况下同时保证跨度和承重？”对应字段：`driving_question`。

### 3. 目标产出

明确最后要交什么，常见包括实物作品、演示视频、测试记录、设计说明和反思总结。对应字段：`expected_outcome`。

### 4. 约束条件

列出材料、尺寸、时间、预算、安全边界和提交形式等限制，让设计取舍可理解、作品可比较。对应字段：`constraints`。

### 5. 完成标准

区分“完成”和“优秀”，建议列 3–5 条。当前没有独立字段；短期可放在 `expected_outcome` 或 `constraints`，阶段清单也可承载局部标准。后续若扩展数据结构，优先考虑独立的 `success_criteria`。

### 6. 推荐脚手架

脚手架帮助用户启动，却不能规定唯一路线。推荐分三类：参考项目、前置技能、资料卡。当前承载字段是 `resources`（`project` / `skill` / `reference` 三分类，每条可带 `description`）；资料卡由 `learning_resources` 表承载，详情页为 `/resources/[id]`。创建挑战时列 3–6 个脚手架，逐个匹配实体；没有实体就补资料卡或配套示例项目，不留空链接。

只有在启动门槛高、具备独立复用价值，并且示例展示方法而非最优解时，才新建配套示例项目；否则使用案例资料卡。

### 7. 分层提示

默认折叠，用户卡住时逐层展开：轻提示提醒方向，中提示给比较思路，强提示给典型方法或常见坑。当前可挂在 `stages[].hint` 或 `resources` 中；强提示不能直接给出唯一答案。

### 8. 反思与迭代

至少记录最初方案、遇到的问题、做过的修改、修改后的结果和最终反思。对应字段：`problem_statement`、`iterations`、`reflection`。

## 三、推荐路线与页面顺序

脚手架是遇到问题时回查的支撑库，不是必须逐项完成的课程路线。合理路径是：先理解任务，提出自己的方案，尝试并发现卡点，回查对应项目/技能卡/资料，再返回挑战继续做，最后提交作品和迭代记录。

长期挑战详情页建议按以下顺序：Hero（标题、摘要、难度、类型、主行动）；任务说明（情境、驱动问题、目标产出）；约束与完成标准；推荐脚手架；阶段推进；提交要求；作品墙/示例成果；行动区。阶段是建议推进方式，不是唯一解法。

## 四、当前实现入口

当前挑战工作流使用同一次 Journey 保存阶段进度和产出，开发时以以下入口为准：

| 能力 | 当前入口 |
|---|---|
| 挑战详情与 PBL 信息 | `app/pbl/[id]/page.tsx`、`components/features/challenge/pbl-info.tsx` |
| 阶段工作台 | `components/features/challenge/stage-workspace.tsx` |
| 阶段产出与自动保存 | `app/api/challenges/[id]/stages/[index]/route.ts`、`challenge_stage_progress` |
| 阶段完成清单 | `stages[].checklist` 与工作台完成动作 |
| 导师阶段指导 | 小迪 `pbl.focus_current_stage` handler，由当前场景 capability 注册和分发 |
| 作品提交 | `app/pbl/[id]/submit/page.tsx` 与挑战提交 API |
| 管理与资源配置 | `components/admin/challenge-management.tsx`、资料卡管理 |

阶段只在前置阶段完成后解锁；未解锁阶段显示剩余步数提示。阶段产出支持防抖保存，主动作是“完成这步”，并配有成功标准清单。导师工具提供拆题、提示、整理和阶段反馈，输出受控参考卡，不代替用户完成方案。最终作品与阶段记录进入统一作品/记录体系。

挑战审核、互动资格和作品公开状态遵循全局规则；不要另造会员、XP、Trust 等权限等级。评分、奖励和 STEAM 展示的实际行为以当前接口与迁移为准，新增行为先核对对应代码和数据库约束。

## 五、内容生产规则

- **标题**体现任务，不只写学科主题，如“轻量承重桥挑战”“未来社区规划挑战”；避免“桥梁设计”“城市规划”。
- **摘要**同时包含场景、行动和目标，避免只有口号。
- **脚手架**每个挑战提供 3–6 个强相关项，不让用户误以为必须先学完一堆内容。
- **提示**默认折叠，按轻、中、强顺序逐层暴露。
- **反思**询问最初方案、失败位置、修改内容、效果原因和下次优先改动，不只问“学到了什么”。

## 六、完整示例：轻量承重桥挑战

### 任务背景

学校要跨过一条 30cm 宽的小沟，需要一座尽量轻但能承重的桥。

### 驱动问题

怎样在材料有限的情况下，同时提高桥的跨度、稳定性和承重能力？

### 目标产出

- 一座桥梁模型
- 一段承重测试视频
- 一份结构说明
- 至少一次迭代记录

### 约束条件

- 只能使用纸张、冰棍棒、胶带和白胶
- 总材料数量受限
- 桥面必须跨越 30cm
- 测试时桥面不能明显塌陷

### 完成标准

- 稳定跨越 30cm
- 至少承受 500g
- 有清晰测试记录
- 能解释结构选择
- 至少完成一次修改迭代

### 推荐脚手架与提示

- 参考项目：`纸张折叠桥`
- 前置技能：`桁架结构受力入门`
- 资料卡：`常见桥型对比`
- 轻提示：想一想桥面变形最严重的位置在哪里。
- 中提示：对比平板结构和三角结构在受力时的差异。
- 强提示：如果桥面中段下垂，优先考虑提高截面高度或加入桁架。

### 反思要求

说明第一版为什么失败或不稳定，改动了哪些结构，以及承重结果如何变化。

## 七、快速验收

一个挑战应同时满足：用户知道要解决的真实问题；知道最后要提交什么；有脚手架但没有固定路线；需要解释方案并记录试错；不同用户可以提交明显不同而都合理的结果。如果没有开放设计空间，它仍是教程；如果没有产出和反思要求，它只是活动标题。
